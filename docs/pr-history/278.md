# PR #278 - Add Everyday Fragments as an atlas-scoped record beside Journeys

- **Source head:** `67c2c519ea209209faace563a9a31906a3803cc4`
- **Scope:** Issue #234. New atlas-scoped `everyday_fragments` table (occurrence date, coordinates, nullable place label, nullable note, nullable `home_base_period_id` with `on delete set null`, no title column) with drizzle-kit migration `0016_red_mister_fear.sql` and its `meta/` snapshot. `media_assets.journey_id` relaxed to nullable, nullable `everyday_fragment_id` added with cascade delete, and one `media_assets_single_owner` CHECK enforcing that exactly one owner is set and that a fragment-owned asset carries no `route_point_id`. Every reader of the now-nullable column narrowed explicitly in `server/repositories/journey-repository.ts`, `server/routes/uploads.ts` and the `shared-journey-repository.ts` row loader, with `buildSharedJourneyView` byte-identical. New pure `src/journey/everydayFragment.ts` holding reason-coded validation and `groupEverydayFragmentsByHomeBase`, which calls #231's `resolveHomeBaseForDate` and defines no second date resolver. New `server/repositories/everyday-fragment-repository.ts` and `server/routes/everyday-fragments.ts` mounted at `/api/everyday-fragments`, with the Atlas taken only from `requireAtlasAccess` and validation refusals mapped through `server/app.ts` `onError`. `CONTEXT.md` gains the **Everyday Fragment** definition and its Journey-only media invariant is replaced by the one-owner rule.
- **User-visible change:** An everyday moment can be recorded against a place and a date without creating a Journey, without a title and without a route, and it is grouped under the Home Base period that held on its own date. The Journey list still contains only Journeys, and a guest share link still exposes no fragment data.
- **Review fixes:** Two Codex P2s, both confirmed and fixed in `189f28e`. The Home Base association was verified for atlas ownership only, so a same-atlas period whose interval did not contain `occurredOn` was persisted and then disagreed with what `resolveHomeBaseForDate` answers for that date; coverage is now decided by #231's own `homeBasePeriodCoversDate` inside the same atlas-locked transaction and refused with a 409 `EVERYDAY_FRAGMENT_HOME_BASE_MISMATCH`, since the document is well formed and what is wrong is the timeline it claims. And `0000-01-01` passed the JavaScript round-trip date check while the PostgreSQL `date` type has no year zero, which would have reached the database as a generic 500 instead of the reason-coded 400; year `0000` is now refused in the validator. Both are pinned by named tests. A third commit fixes the assertion in the integration test rather than any product code: the three CHECK cases really were refused by PostgreSQL, but Drizzle wraps a driver error so the constraint name is on the wrapped `cause` and not in the thrown `message`, and matching the message would have passed on any failed insert.
- **Follow-up:** `server/routes/home-bases.ts` `validDate` accepts year `0000` for the same reason the fragment validator did, so `POST /api/home-bases` with `0000-01-01` still answers 500. It is #231's code, untouched here to keep this PR to one feature, and worth a one-line fix in whichever change next visits that module. The multipart upload pipeline is unchanged (`media_uploads.journey_id` stays non-null), so V1 has no API path that creates fragment-owned media; the CHECK is exercised by direct inserts in the integration test. Consequently `server/services/delete-atlas.ts`, which collects storage refs per Journey, would not sweep a fragment-owned object -- unreachable today, and to be handled by whichever issue gives fragments an upload path. The semantic-zoom density reveal near Home, the lightweight viewer and its Atlas entry point, the EXIF-driven suggestion flow and Journey conversion are out of scope by the feature's own fence.
- **Validation:** `./init.sh smoke` here (`pnpm typecheck`, `git diff --check`, `node scripts/pr-history.mjs validate-all`). CI is authoritative for behaviour: the `core` lane applies the generated migration to an isolated PostgreSQL 17 and runs `src/journey/everydayFragment.test.ts`, `server/routes/everyday-fragments.test.ts` and `server/tests/everyday-fragments.integration.test.ts`, and the `ledger` lane validates this file. No test, browser, database or object store was run locally.
