# PR #213 - Book Quick Recap chapters at the durations playback will spend

- **Source head:** `7f5f3a9817368b5ec5791347600163fd626a4051`
- **Scope:** `DeterministicQuickRecapInput` (`src/journey/autoEditPlan.ts`) gains an optional `routePointGeometry`, a `Record<string, QuickRecapRouteGeometryV1>` keyed by route point id so it cannot fall out of step with `routePointIds`, carrying `angularDistanceFromPrevious` and `noteLength`. `buildDeterministicQuickRecapPlan` books each route chapter's `camera.durationMs` and `arrival.durationMs` through `resolveNarrativeTiming({ mode: "quick-recap", tempo, ... })` with that geometry - the same call the runtime makes - so `plannedDurationMs` is the recap's real length; the greedy `baseOverhead` sums those same per-chapter numbers instead of `routePointIds.length * (travelBase + arrivalBase)`. The intro chapter stays `hold` at 0 ms and `AutoEditPlanV1` stays at schema version 1 with no field additions. `quickRecapPlayback.ts` derives the geometry from the Journey via a new `quickRecapRouteGeometry()` helper that measures each leg against the previous *candidate* route point, not the canonical neighbour, because a media-less route point is dropped from the projected Journey and the camera flies past it. `quickRecapStepDurationMs()` now reads the booked `camera.durationMs` / `arrival.durationMs` back off the frozen plan instead of re-resolving them, leaving the resolver one job there: a dwell the plan did not pin. `CAMERA_MS`, `ARRIVAL_MS`, the dwell tables and `PLAYBACK_PACING` are untouched - only no longer read for this budget; their deletion belongs to the parallel PR 6. Follow-up to #208 and #210, sections 2, 3 and 6 of the shared narrative timing plan.
- **User-visible change:** A Quick Recap now lasts as long as it says it will. Reproducing #210's 5-airport fixture (HKG-LHR-JFK-NRT-SYD, 33-character note per stop, 3 photos each) on `origin/main`: planned 40700 ms against a runtime 45384 ms at `standard` (+4684 ms), +3243 ms at `fast`, +6317 ms at `immersive`, i.e. a 47984 ms wall clock at `standard` and 49217 ms at `immersive` against a 45000 ms promise. After this change the drift is 0 ms at all three tempi and the wall clock lands at 36043 / 44384 / 43217 ms. Paying the real cost fail-closed keeps fewer optional photos on long-haul journeys: on that fixture `standard` keeps 12 instead of 14 and `immersive` 5 instead of 7, `fast` is unchanged at 15. Denser fixtures barely move - the repo's own `point()` helper spaces route points about 0.023 rad apart, worth roughly +11 ms of camera at `standard` - so the existing suite's totals shift by tens of milliseconds and the 9-point over-budget fixture stays over budget.
- **Review fixes:** None yet; opened straight from the brief.
- **Follow-up:** `over-budget` now trips on journeys that previously squeezed through on an under-booked estimate. That is the correct fail-closed outcome for the 45 s promise, but the product answer for a long intercontinental recap is probably a shorter dwell or fewer stops rather than a Full Playback fallback, which is a product decision this PR does not take. #210's observation that `QUICK_RECAP_PROFILES` seeds `travelBaseMs: 1000` identically at all three tempi still stands: the camera term for a short leg barely answers the tempo control, and giving the quick-recap profile a per-tempo travel floor remains open. `routePointGeometry` is optional, so a caller that omits it still books the quick-recap floor for both beats and re-introduces the drift this PR removes; `prepareQuickRecapPlaybackResult` is the only production caller today, and the planner has no way to detect a caller that should have supplied geometry.
- **Validation:** `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm vitest run src/` (42 files, 566 tests, all passing), `git diff --check`. New coverage in `quickRecapPlayback.test.ts`: the plan total equals the sum of runtime step durations at all three tempi on a 5-city intercontinental fixture, asserting alongside it that no non-framing step is left unpriced so a drift between the step stream and the plan's chapters cannot read as parity; a long-haul leg books more camera than a nearby one; an annotated stop books a longer arrival than a note-free one and a longer note more than a shorter one; the recap still fits `QUICK_RECAP_TARGET_MS` once intro and outro are added back; `validateAutoEditPlanV1` accepts the geometry-priced plan, with positive route camera and arrival durations and `trim.inMs === 0`; and a recap that drops a media-less middle route point books the leg it actually flies (`p0` to `p2`) rather than the canonical neighbour. One #210 test changed: `"resolves travel and stop differently at every tempo"` read a single `standard` plan at three tempi, which is exactly the reinterpretation this PR removes, so it now rebuilds the plan per tempo the way `handlePlaybackTempoChange` does. The #202 photo-first ordering and #208 grammar tests are unchanged and green. The before/after numbers above were measured by running the shipped fixture against `origin/main`'s `autoEditPlan.ts` and `quickRecapPlayback.ts` in a scratch directory, which was deleted before the commit. No dev server, browser or database checks ran locally; GitHub CI remains the authoritative integration and build verification.
