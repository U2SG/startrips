# PR #208 - Validate Quick Recap chapter grammar without fixed timings

- **Source head:** `4b8dda198c3b79c557819c885133efe49881de87`
- **Scope:** PR 2 of the S1 shared narrative timing plan (`docs/plans/2026-09-03-shared-narrative-timing-resolver.md`), touching `src/journey/autoEditPlan.ts` and `src/journey/autoEditPlan.test.ts` only. Adds semantic choreography checks to the `quick-recap` branch of `validateAutoEditPlanV1`: a journey-intro chapter (`routePointId === null`) must be `camera.primitive === "hold"` with `durationMs === 0` and no `arrival`; a route chapter must use a route travel primitive and carry an `arrival` with boolean `showPlaceLabel` / `showNote`. The travel grammar is expressed as `isRouteTravelPrimitive()`, the complement of `hold` rather than a curated list, so `short-arc` (#126's `nearby` choreography) is accepted without a further validator change. Being a complement rather than a membership test, it is bounded by the unconditional `AUTO_EDIT_CAMERA_PRIMITIVES` check in the same chapter loop, which rejects a primitive outside the vocabulary; the helper names that dependency and a test proves it. Removes all four millisecond equalities named in plan section 3 - quick-recap `dwellMs !== IMAGE_DWELL_MS[tempo][role]`, `trim.outMs !== min(sourceDuration, VIDEO_DWELL_MS[tempo])`, and the `camera.durationMs !== CAMERA_MS` / `arrival.durationMs !== ARRIVAL_MS` pair that the code actually imposed on the `full` branch, not on `quick-recap`. `itemDuration()` and the plan's camera and arrival durations now resolve through `resolveNarrativeTiming({ mode: "quick-recap", ... })` from #205; the finite non-negative duration checks, the quick-recap selection re-derivation and the `plannedDurationMs` recompute all stay, the last as the anti-forgery check. `AutoEditPlanV1` stays at `schemaVersion: 1` with no field added or removed - only the accepted range of `camera.durationMs`, `arrival.durationMs`, `dwellMs` and `trim.outMs` widens from one exact value to any finite non-negative number consistent with `plannedDurationMs`, a strict relaxation.
- **User-visible change:** None. `validateAutoEditPlanV1` has no production caller - `git grep` finds it only in `autoEditPlan.test.ts` - and a zero-distance, zero-note quick-recap beat resolves to exactly the previous 1000 / 800, so every emitted plan is byte-identical.
- **Review fixes:** None yet; opened for review.
- **Follow-up:** `CAMERA_MS`, `ARRIVAL_MS`, `IMAGE_DWELL_MS` and `VIDEO_DWELL_MS` are deliberately kept although no code reads them. Their only remaining consumer is `narrativeTiming.test.ts`, which asserts the resolver's quick-recap profile against them instead of against copied literals, and that file is outside this PR's two-file scope; their doc comment now says so. Whichever PR next edits `narrativeTiming.test.ts` should delete all four, which completes the deletion PR #205's ledger assigned to this PR. #166 is only partly closed: its "nearby vs long-haul legs must not collapse to one camera duration" item is proven at the resolver level but not at the Quick Recap plan level, because `buildDeterministicQuickRecapPlan`'s input carries no route geometry or notes - threading tempo, distance and note length in is PR 4 (`quickRecapPlayback.ts`, `useJourneyPlaybackDirector.ts`). For the same reason the plan-level tempo assertion covers dwell and total only: `QUICK_RECAP_PROFILES` carries `travelBaseMs: 1_000` / `arrivalBaseMs: 800` identically across all three tempi, so camera and arrival cannot yet differ per tempo, and the test asserts that flatness explicitly rather than a difference the data cannot support. PR 4 must also re-check the greedy budget's `baseOverhead`, which still assumes a flat camera plus arrival per route point. PRs 3, 5 and 6 are unchanged from the plan.
