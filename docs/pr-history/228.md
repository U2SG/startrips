# PR #228 - Honour a declared video trim during playback, then allow a non-zero in-point

- **Source head:** `c2e79650f1c84382de0ea350c426613c36a212d9`
- **Scope:** #195 Phase 2. New pure `src/journey/videoTrimPlayback.ts`: `resolveVideoTrim()` turns a plan item's declared `[inMs, outMs)` plus the media element's real `duration` into either a playable segment or one of three named degradations (`no-trim`, `unknown-source-duration`, `source-shorter-than-in-point`), and `videoTrimEntryAction()` / `videoTrimProgressAction()` / `videoTrimSegmentDurationMs()` / `videoTrimHoldsStep()` answer what the transport must do, all in the default node test environment. `quickRecapPlayback.ts` gains `quickRecapStepTrim()` over a shared `quickRecapItemForStep()` lookup that `quickRecapStepDurationMs()` now uses too. `JourneyPlaybackOverlay.tsx` gains a `mediaTrimResolver` prop, a `videoTrimSeek` state with its own bounded watchdog, `onLoadedMetadata` / `onSeeked` handlers and trim handling inside `onTimeUpdate`; its hold effect gives a trimmed video beat segment ownership instead of `ended` ownership. `LivingAtlasApp.tsx` supplies the resolver from the active Quick Recap plan. `autoEditPlan.ts` drops the `trim in-point unsupported` rule in the following commit. New `src/journey/videoTrimPlayback.test.ts`; new cases in `quickRecapPlayback.test.ts` and an inverted, extended case in `autoEditPlan.test.ts`. No schema change, no server file touched.
- **User-visible change:** A Quick Recap video beat now ends at the plan's out-point instead of playing the source to its end, so a recap containing a video runs for the duration it was budgeted and accepted at. Nothing else changes today: the planner still emits `inMs: 0` on every item it produces, so no plan in production carries a late in-point yet. Full Playback is untouched — it has no Edit Plan, so no trim is declared and its video chapters still end on the real `ended` event.
- **Review fixes:** Codex raised one P1, verified against the code before acting and valid: releasing the director hold once the element reached the in-point handed the beat to the wall-clock timer, but nothing reacquired that hold when playback stopped progressing. A buffering element leaves `currentTime` stationary while the timer keeps spending `outMs - inMs`, so a 3.5 s beat could advance having played almost none of its segment, and before the existing 4 s stall watchdog fired at all. Fixed in `f5fdf903cc25ec81eff3078223070b117306e152`: a fourth `buffering` state reacquires the hold on `waiting` and `stalled`, and `playing` or a real `timeupdate` — the only event that proves `currentTime` moved — releases it. A self-review then found that this fix had a regression of its own against acceptance 6, which names pause explicitly: `waiting` and `stalled` also fire around an ordinary pause and around the refill that follows a resume, so a slow refill could drive a beat that was playing correctly into the media fallback and lose its trim on a pause the viewer expected to be transparent. `c2e79650f1c84382de0ea350c426613c36a212d9` closes that: `videoTrimBuffersOnStall()` makes a not-progressing signal a stall only while the beat is meant to be moving, `videoTrimStatusAfterPauseChange()` stops any beat carrying `buffering` across a pause so the watchdog window always measures the resume, and the escape now degrades to `ended` ownership without reaching for the media fallback that the pre-existing `stalled` watchdog already owns. `seeked` also re-runs the entry rule instead of assuming one seek landed - a seek lands on the nearest decodable frame and can fall short of the in-point - bounded to the holding states so it cannot loop.
- **Follow-up:** No real video duration is persisted anywhere, so every video digest is still built with `QUICK_RECAP_PENDING_VIDEO_DURATION_MS` and a plan's trim is booked against a number that is not the media's. This PR makes that survivable at playback time by clamping the out-point onto the element's real duration and by degrading when the in-point sits past it, but the measurement itself is #195's own remaining Phase 2 work and is not filed separately. Producing a non-zero in-point is highlight planning's job and no code does it yet, so the capability ships ahead of its first caller by design — that ordering is what acceptance 3 of the queue entry requires. A video beat still prefetches the whole source even when only a segment plays.
- **Validation:** Locally only `./init.sh smoke` — `pnpm typecheck` (client and server projects), `git diff --check`, and `pr-history validate-all`. No local test run, dev server, browser, database or Docker; CI is authoritative for this repository and runs the full suite, the eight browser QA lanes and the build. The non-zero in-point is exercised by hand-authored plans in `quickRecapPlayback.test.ts` and `autoEditPlan.test.ts`, asserting that the director's `outMs - inMs` budget and `videoTrimSegmentDurationMs()` are the same number, that entry seeks to the in-point, that a re-entered beat past its out-point is repositioned, and that the validator now accepts the exact late-in-point plan it used to reject while still rejecting one outside the source bounds. Full mode is pinned by the untouched `full video trim mismatch` case.
