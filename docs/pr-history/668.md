# PR #668 - Backfill previews for originals the browser never finished

- **Source head:** `0be534f4f2366c8351877fb441099a724ced1141`
- **Scope:** `server/services/media-preview-backfill.ts` adds a bounded sweep started from `server/index.ts`: every five minutes, up to eight image assets whose Journey is not marked for deletion are taken through the existing protocol from the API process (`beginAssetPreview`, a `sharp` render into the issued still down the browser's JPEG quality ladder, the signed single-object PUT, `completeAssetPreview`). Candidates are `none` rows older than ten minutes, and `pending` rows whose current generation's `media_preview_writes` record has expired past that grace or no longer exists, so a generation a browser began moments ago on an old asset keeps its claim. `beginAssetPreview` now returns the `storageKey` it claimed; the sweep builds that generation's row from the issued values and never re-reads the asset, so every later write is a compare-and-swap on exactly that key and a concurrent browser producer that supersedes it leaves the sweep reporting `superseded`. Undecodable pixels (metadata fine, render throws), stills that fit no quality, oversized sources and server-observed unplannable dimensions are recorded as `failed` through the new `failAssetPreview` export. `MEDIA_PREVIEW_BACKFILL_ENABLED` (default on with configured storage) switches the sweep off. `sharp@0.35.5` is added; it ships prebuilt binaries as optional packages, so `onlyBuiltDependencies` and the Dockerfile are unchanged.
- **User-visible change:** Photos uploaded before #667 gain a 640 px preview within minutes of deployment, so Playback and the Story stop waiting on their full originals (the Bryce Canyon stall).
- **Review fixes:** Codex P2 ×3 and one owner-confirmed concurrency P2, all in 0be534f4: pending staleness is judged by the current generation's write record rather than the asset's `createdAt`; render-time decode errors become decided failures; `INVALID_PREVIEW_REQUEST` from server-measured dimensions becomes a decided failure instead of an endless retry; and the pass binds render, write and completion to the generation it claimed instead of re-reading the row, so a browser's newer generation is never completed or cleared by the sweep. Integration tests cover each: expired-vs-live write records in candidate selection, a truncated JPEG, and a supersede during the sweep's PUT leaving the browser's generation `pending` and untouched.
- **Follow-up:** After deployment, confirm on the host that `preview_state = ready` rows appear and `media/previews/` gains objects; #669 names the decode wait while any original is still unbackfilled.
- **Validation:** Local: `pnpm add sharp@^0.35.5`, `pnpm typecheck`, `git diff --check`, ledger validators; `sharp` 0.35.5 / libvips 8.18.7 loads on Windows, renders the 2048×1024 fixture to a 640×320 JPEG, and throws `premature end of JPEG image` on the truncated fixture used by the decode-failure test.
