# PR #598 - Duck the Journey soundtrack under audible foreground video

- **Source head:** `ce618498d6eb8650cc44238d8d9f49d293a5009a`
- **Scope:** Issue #596. `src/journey/soundtrackDucking.ts` holds the policy - when a foreground video counts as audible, the duck factor, and the attack/release ramp, which is time-based rather than tick-based so two surfaces evaluating the same moment agree. `src/journey/soundtrackDuckingController.ts` holds the state machine that drives one soundtrack element's volume by polling live state each frame instead of listening for pause/ended/mute events. Wired into Story (inline and immersive) and Journey Playback / Quick Recap / Full Playback, one controller per surface. `scripts/qa-soundtrack-ducking.mjs` is the browser lane, and `ProductQaPreview` gains a fixture affordance that attaches a soundtrack and can swap its identity to force a real remount.
- **User-visible change:** A Journey soundtrack steps down smoothly while a foreground video is audible and returns to the member's own level when the video stops, is paused, muted or ends. It follows the level the member sets rather than overriding it, including a change made while the duck is already in effect.
- **Review fixes:** Four defects were found and fixed against evidence rather than assumption. The Story wiring copied `storyVideoRef.current` during render, but React attaches those refs in the commit phase, so the copy was null the first time a video appeared and stale across an inline-to-immersive switch - the first video in a Story could simply never duck. Both surfaces passed a hard-coded `getBaselineVolume: () => 1`, which made "the member changed the volume while ducked and got the new level back" unreachable in the product while the policy test for it passed; the controller now owns the baseline, treating any level it did not write as the member's. A replacement soundtrack element, produced by a re-key, sat at the browser default while the controller still believed it was ducked. And when the member changed the level mid-duck, the controller adopted the new baseline but left `current` and `lastWritten` behind, so the ramp restarted from a stale origin every frame and the element never moved - the test for this had the bug written into it as the expected answer and was corrected first.
- **Follow-up:** Nothing from #596's acceptance list is left unasserted. The immersive hand-off is covered on its own page and asserts that exactly one soundtrack element is present, that the controller still drives that same element, and that the duck follows it in. Three defects in the lane itself had to be fixed before any of that was trustworthy, and all three made a correct duck read as a failed one. The settle window asked "did the volume stop moving" rather than "did it arrive", so a linear ramp returned before it got there; it now waits for the level the assertion names and holds it across polls, and each check carries the controller's own view. The Story's autoplay is not sticky and the fixture clip can end mid-window, either of which silently revoked the next assertion's precondition, so the lane now holds the transport itself and reports whether the hold actually took. And simulating `ended` with `defineProperty` installs an own property over the read-only prototype getter that outlives the assertion, so every later check on that page saw a permanently ended element; the proof it was the fixture rather than the product was two contradictory samples at one instant - the DOM reporting two videos ready and playing while the controller reported `foregroundPlaying: false`. `public/` ships no audio file, so the soundtrack's source never decodes in QA: the lane verifies the volume written to a real element under a real transport and does not claim to measure anything audible.
- **Validation:** Acceptance is GitHub Actions only. The `browser-qa / story-media` shard - which carries the ducking lane - is green on the Source head, alongside `core` (generated auth schema, migrations, typecheck, the full `pnpm test`, build), `quick-checks`, `keepsake-render` and the other nine browser lanes; both `production autoplay` jobs are green. `browser-qa / shell-composer` failed on `final-acceptance` with a hit-test against a journey-rail control that does not exist at the mobile breakpoint (`railPresent: false`, `railButtons: 0`, `hitTag: null`) at 320/360/430; the same signature appeared on an earlier commit and passed on re-run, and this branch's diff touches neither the rail nor hit-testing, so it is being re-run rather than treated as a regression. The browser-suite contract from #591 moved from 31 to 32 with the new lane, joined to the existing `story-media` shard so the eight-shard ceiling is unchanged. This final commit changes only this ledger, and the ledger fast path proves the Source CI it reuses.
