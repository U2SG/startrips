# PR #206 - Hide the Playback tempo control in Quick Recap

- **Source head:** `cef6c80cc09f7818353e17cbcc14b804c1c1d795`
- **Scope:** Adds the pure helper `playbackTempoControlVisible(playbackMode)` to `src/journey/playbackControls.ts`, beside the existing `playbackControlsMayAutoHide()` chrome-visibility rule, and uses it in `JourneyPlaybackOverlay.tsx` to conditionally render the tempo control. The whole `<label className="journey-playback__tempo">` is removed rather than just the inner `<select>`, so no empty styled label is left in the control row. Because `.journey-playback__controls` is a fixed five-column grid with a second, narrower definition under `max-width: 760px`, both definitions gain a `.journey-playback[data-playback-mode="quick-recap"]` variant that drops the tempo column; the overlay root already emits that data attribute. `LivingAtlasApp.tsx` is not touched.
- **User-visible change:** The playback tempo dropdown no longer appears while a Quick Recap is playing. It is unchanged in Full Playback. Nothing else about Quick Recap timing changes - the control was only ever moving intro and outro there.
- **Review fixes:** Two corrections were made before the commit. First, the plan prescribes a new `quickRecap: boolean` prop passed from `LivingAtlasApp.tsx` on the premise that "the overlay does not know its mode today". That premise held at the plan's baseline `0805471` but not at this PR's baseline: `JourneyPlaybackOverlay` already accepts `playbackMode?: "full" | "quick-recap"`, already derived from `playbackQuickRecap` at exactly the render site the plan points at. A second prop would have been duplicate state, so the existing one is reused and the deviation is recorded here and in the PR body. Second, the plan describes hiding "the tempo `<select>`", which would have left the styled `<label>` behind and, more seriously, would have shifted the progress bar into the tempo column while leaving an empty trailing column, since the control row is a fixed-column grid rather than a flex row. Both grid definitions therefore gain a quick-recap variant.
- **Follow-up:** PR 4 of the shared narrative timing plan (Quick Recap tempo wiring) owns the reverse change. Once `quickRecapStepDurationMs()` takes a tempo and resolves travel, arrival and dwell through the resolver, the control becomes meaningful again: `playbackTempoControlVisible()` is the single place to re-show it, and the two CSS variants come back out with it. Decision D1 (target duration wins over tempo in Quick Recap) means that re-showing the control also implies a plan rebuild on tempo change, which is PR 4's problem, not this one's.
