# PR #326 - Record the Journey rail's DOM state at the flaking final-acceptance activation

- **Source head:** `a9cdf98cc682e257db4422fa0601dd0c0ba5745d`
- **Scope:** Implements ST-062 / issue #325, the source issue for this PR, and touches `scripts/qa-post-login-controls.mjs` only. The `activateControl` helper inside `verifyFinalAcceptanceMobileFlow` now reads `.living-atlas__journey-rail` — presence, computed `display`/`visibility`/`opacity`, bounding box, inertness, rail button count, count matching the target title, the `.living-atlas` `class` and `data-mobile-v2`, and the target button box — in the same browser evaluation as the existing actionability fields. A third `recordRailState` parameter, set only at the `desktop target journey control` call site, emits that object as `[qa-post-login] final:<viewportLabel>:journey-rail-state <json>` on stderr, and the same object is appended to the `is not actionable` error. No retry, poll, extra wait or raised timeout was added.
- **User-visible change:** None. No file under `src/` or `server/` changes.
- **Review fixes:** Codex thread 3997921470 (P2) showed that capturing the rail in a second `page.evaluate` lets the DOM recover between tasks, so a failing iteration could report a healthy rail and defeat the classification the issue asks for. Commit `a9cdf98` merges the rail read into the actionability evaluation and removes the separate `captureJourneyRailState` helper; the marker line moved with it, from just before `activateControl` to just before the click inside it.
- **Follow-up:** The instrument classifies the flake, it does not fix it. Issue #325 stays open until an occurrence is captured and read.
