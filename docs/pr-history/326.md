# PR #326 - Record the Journey rail's DOM state at the flaking final-acceptance activation

- **Source head:** `51cfe5fc66ea4332f9e5a07a37ffe62d509e24dc`
- **Scope:** Implements ST-062 / issue #325, the source issue for this PR, and touches `scripts/qa-post-login-controls.mjs` only. `activateControl` inside `verifyFinalAcceptanceMobileFlow` takes a third `recordRailState` parameter, set only at the `desktop target journey control` call site. On that path it resolves the rail and the target button together in one page-scoped `page.evaluate`, returning the actionability fields alongside a rail snapshot — presence, computed `display`/`visibility`/`opacity`, bounding box, inertness, rail button count, count matching the target title, the `.living-atlas` `class` and `data-mobile-v2`, and the target button box — so an absent target yields an explicit missing state instead of preventing the observation. The snapshot is logged as `[qa-post-login] final:<viewportLabel>:journey-rail-state <json>` immediately before the click, and appended to the `is not actionable` error. Every other call site keeps the original locator-scoped probe byte for byte. No retry, poll, extra wait or raised timeout was added.
- **User-visible change:** None. No file under `src/` or `server/` changes.
- **Review fixes:** Codex thread 3997921470 (P2) showed that capturing the rail in a second `page.evaluate` lets the DOM recover between tasks, so a failing iteration could report a healthy rail; `a9cdf98` merged the rail read into the actionability evaluation. Codex thread 3998026549 (P2) then showed that an element-scoped evaluation cannot run at all when the rail is unmounted, so `railPresent:false` was unreachable and the scroll step would block first; `51cfe5f` resolves rail and target together in one page-scoped task, which keeps the single-DOM-state guarantee the first thread asked for while making a missing target reportable.
- **Follow-up:** The instrument classifies the flake, it does not fix it. Issue #325 stays open until an occurrence is captured and read.
- **Validation:** `./init.sh smoke` (`pnpm typecheck`, `git diff --check`, `node scripts/pr-history.mjs validate-all`) and `node --check scripts/qa-post-login-controls.mjs` locally. Browser behaviour is CI-only and authoritative: the `browser-qa / final-acceptance` lane log captured at `.agent-artifacts/st-062/final-acceptance-lane.log` is the evidence that the `journey-rail-state` marker is emitted in all four viewport iterations (320, 360, 390, 430), alongside `ledger`, `core` and `verify` in `gh pr checks`.
