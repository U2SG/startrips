# PR #326 - Record the Journey rail's DOM state at the flaking final-acceptance activation

- **Source head:** `80d03e125e6f5529498217c989a8c7b94a499090`
- **Scope:** Implements ST-062 / issue #325, the source issue for this PR, and touches `scripts/qa-post-login-controls.mjs` only. `activateControl` inside `verifyFinalAcceptanceMobileFlow` reads `.living-atlas__journey-rail` inside the `locator.evaluate` that already computes the actionability fields, returning a rail snapshot alongside them — presence, computed `display`/`visibility`/`opacity`, bounding box, inertness, rail button count, count matching the target title, the `.living-atlas` `class` and `data-mobile-v2`, and the target button box. A third `recordRailState` parameter, set only at the `desktop target journey control` call site, logs that object as `[qa-post-login] final:<viewportLabel>:journey-rail-state <json>` immediately before the click; the snapshot is appended to the `is not actionable` error at every call site. The scroll and actionability paths are byte-identical to `main`, so the activation's timing is unchanged. No retry, poll, extra wait or raised timeout was added.
- **User-visible change:** None. No file under `src/` or `server/` changes.
- **Review fixes:** Codex thread 3997921470 (P2) showed that capturing the rail in a second `page.evaluate` lets the DOM recover between tasks, so a failing iteration could report a healthy rail; `a9cdf98` merged the rail read into the actionability evaluation. Codex thread 3998026549 (P2) then showed that an element-scoped evaluation cannot run when the rail is unmounted, because the pre-existing `locator.evaluate(scrollIntoView)` blocks first, leaving `railPresent:false` unreachable. `51cfe5f` answered it by resolving rail and target together in one page-scoped task, but that also deleted the locator's implicit wait for the target to attach, so a transient unmount that previously self-healed would throw — an observability change altering when the instrumented step fails, which ST-062 acceptance 4 forbids. `80d03e1` reverts to the element-scoped read and records the finding as a stated residual on the thread and in the PR body instead.
- **Follow-up:** The instrument classifies the flake, it does not fix it. A rail absent long enough for the locator to time out still yields no snapshot; that case is distinguishable by its error signature (a Playwright locator timeout rather than `is not actionable`), and closing it needs the restructure acceptance 4 freezes. Issue #325 stays open until an occurrence is captured and read.

Browser behaviour is CI-only and authoritative: the `browser-qa / final-acceptance` lane log captured at `.agent-artifacts/st-062/final-acceptance-lane.log` is the evidence that the `journey-rail-state` marker is emitted in all four viewport iterations (320, 360, 390, 430), alongside `ledger`, `core` and `verify` in `gh pr checks`.
