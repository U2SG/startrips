# PR #215 - Add the guest read-only journey payload behind a share grant

- **Source head:** `d1b0231ddf613beae61744d5a699b4bfa0e2e335`
- **Scope:** Phase B of #200, server only. New `server/repositories/shared-journey-repository.ts` holds an explicit guest read model: hand-written `SharedJourney`, `SharedRoutePoint`, `SharedJourneyMedia` and `SharedJourneyView` types, a pure `buildSharedJourneyView` that nests route points and media under their journey and resolves `previousJourneyId`/`nextJourneyId` inside the granted array, and `loadSharedJourneyView`, which selects only guest-safe columns, joins `share_grant_journeys` to `journeys` with `atlas_id` compared as well as the grant, filters `deletion_started_at`, orders by the grant's stored `sort_order`, and scopes the route-point and media queries by the resolved journey ids. `server/routes/shares.ts` gains `GET /journeys` on the existing `sharedRoutes` group, a `sharedRoutes.use("*")` middleware that sets `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow` before the handler runs so the generic unavailable 404 built by the global `onError` carries them too, and a `recordShareAccess` helper now shared by `/grant` and `/journeys`; the two header lines that were inline in `/grant` are removed as the middleware sets them. `docs/cross-feature-assumption-audit.md` rows 8, 9 and 10 and the `Downstream share surfaces` gap are updated to cite the new tests and to state what they still do not cover. `server/authorization/share-access.ts` exports its `shareUnavailable()` factory so the read can raise the same generic error. No schema change, so no migration and no regenerated `server/db/auth-schema.ts`. No client file is touched.
- **User-visible change:** None yet. The endpoint has no consumer: the guest viewer is phase D. What changes for a recipient later is that a share link resolves to exactly the granted journeys, their routes and their media, with navigation that cannot leave the granted set.
- **Review fixes:** One inline review thread, 3933510066 from the Codex connector, P1, on `server/repositories/shared-journey-repository.ts`: authorization, the journey selection and the child reads were three separate statements, so an owner withdrawal committing between them could be missed. Verified against the code and accepted in part, fixed in `d1b0231`. The three reads now run in one `repeatable read`, `read only` transaction whose first statement re-evaluates the grant through `evaluateShareGrant`, which both fixes the snapshot and makes the authorization decision part of it, so the payload and the decision describe one instant instead of three; `read committed` would not have done this, because each statement takes its own snapshot. The part not accepted is the thread's stated consequence: no transaction can prevent an answer that was already in flight when the revoke committed, so the residual window is inherent rather than a defect of the previous code, and it was already bounded by design — #200 assigns bounding what has already been issued to the short presign TTL of phase C. The previous code could also not leak outside the grant: the journey set was the authority and the child queries were scoped by its ids, no code path ever updates `journeys.atlas_id`, and V1 forbids mutating grant membership. A new integration case, `refuses a grant withdrawn between authorization and the payload read`, revokes a grant while holding the object `requireActiveShareGrant` had already returned and asserts the read raises `ShareAccessError` and the route answers the generic 404.
- **Follow-up:** Phase C is the share-scoped media read URL with a TTL capped by the remaining grant lifetime — this payload carries media ids and MIME types but no readable URL, so a guest cannot yet fetch a single byte of media. Phase D is the read-only guest viewer, which also owns the document-level `Referrer-Policy` and the `noindex` meta tag; the header on this JSON response is defence in depth and closes nothing on its own, because the token lives in the fragment of the `/share#<token>` document. `GET /api/shared/grant` keeps counting grant membership, so its `journeyCount` still includes a granted journey inside its deletion grace window while `GET /api/shared/journeys` reports the live readable set; phase A's endpoint is left untouched because nothing consumes it and the phase B read is self-sufficient. Share-specific rate limits, the already-open-page expiry transition and the full cross-feature matrix are phase F. Timeline, globe and playback scope closure stay unguarded until a guest viewer exists, which the audit document now records as the remaining half of invariant 8.
