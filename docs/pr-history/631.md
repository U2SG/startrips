# PR #631 - feat(story): open a fresh Journey Story on its cover opening (#555)

- **Source head:** `0948c999efcb81e045d5fc4c89f123bd645d1156`
- **Scope:** Story's cursor now indexes sequence entries instead of canonical media, and Story stage pages are identified by presentation. The Journey cover opening (#620) and the canonical cover can therefore be two pages of one asset. LivingAtlasApp sets an explicit `presentJourneyCoverOpening` signal only on genuine whole-Journey opens; Playback returns and deep links skip the opening. The opening is one-way: wraps land on canonical entry 0. It carries Journey context: no Point chip or note, the Journey note shows, the close-time observation has no asset, and the counter is hidden. The Cover Reveal belongs only to the opening: when a ready generated derivative exists, the opening plays it once per cover revision, then settles on the original. The canonical cover entry, deep links and Playback returns never reveal it, and the Atlas card no longer plays it.
- **User-visible change:** Opening a whole Journey starts on its cover as a Journey-level opening, then continues through every Route Point; the cover appears again later inside its own Route Point.
- **Review fixes:** The maintainer review asked for two things. First, Cover Reveal integration owned by the Journey-cover opening, with no second reveal on the Atlas card. Second, QA for a cover sourced from Journey-level media (`routePointId = null`). Stage playback readiness is compared with the shown page, not the asset, so a video cover can enter fullscreen from the opening. The autoplay reproduction harness steps off the opening only when it is present, because the pinned baseline build predates it, and it requires the opening on the candidate build. Rebased onto main after #630 merged, keeping main's pointer events on the open-Story button.
