# PR #207 - Add expiring read-only share grants

- **Source head:** `1cbe05b7fe22cdfa4cc0fad00e385b5d567c1a4a`
- **Scope:** Phase A of #200, the authorization foundation. Added `share_grants` and `share_grant_journeys` to `server/db/app-schema.ts` with the drizzle-kit generated `server/db/migrations/0011_lethal_chat.sql` plus its `meta/` snapshot and journal entry. Added `server/authorization/share-access.ts` (`generateShareToken`, `hashShareToken`, `parseBearerToken`, the pure `evaluateShareGrant(grant, now)`, `requireActiveShareGrant`, `ShareAccessError`) and `server/routes/shares.ts` (owner `POST`/`GET /api/shares` and `POST /api/shares/:id/revoke`, guest `GET /api/shared/grant`). Wired both route groups and the `ShareAccessError` branch into `server/app.ts` `onError`. Extracted the Atlas row lock as `lockActiveAtlas` in `server/repositories/journey-repository.ts` so the share route serializes on the same row every other Atlas-scoped write does. Added `server/authorization/share-access.test.ts`, `server/routes/shares.test.ts` and `server/tests/share-grants.integration.test.ts`.
- **User-visible change:** None yet. No client code changed and no UI exists; the endpoints are the foundation Phases B-E build on.
- **Review fixes:** Revoke is `requireAtlasAccess(request, "update")` rather than `"delete"`, because `"delete"` is owner-only in `permissions.ts` and would let a member create a link they could never withdraw. `requireActiveShareGrant` joins `atlases` and selects `deletion_started_at` instead of filtering it in `WHERE`, so the deleting-atlas rule lives in the pure decision function and is unit-testable. `journeyCount` counts `share_grant_journeys` rows rather than a join against `journeys`, so a soft-deleted Journey cannot silently shrink a grant's recorded scope. Both the create body and the revoke `:id` are UUID-shape checked before any query, so a malformed id returns 400/404 instead of a Postgres `22P02` surfacing as a 500. `revoked_at` is set with `coalesce`, making a repeat revoke idempotent without a read-then-write window. Two later review findings on the create path were fixed on top. First, the Journey selection and the `deletion_started_at` checks for the Atlas and for every selected Journey ran before the insert transaction, so an Atlas or Journey marked deleting in between produced either a token `requireActiveShareGrant` rejects on sight or a foreign-key failure surfacing as a 500; both checks now run inside the transaction, which first takes the `lockActiveAtlas` row lock and then locks the selected Journey rows `FOR UPDATE`, and a missing, foreign or deleting Journey still answers the same `JOURNEY_NOT_FOUND` 404. A follow-up commit then changed the lock order: those Journey rows are locked in ascending id order, the order the multi-Journey move and undo paths in `server/routes/uploads.ts` already sort their ids into, so an overlapping selection cannot deadlock; the rows are re-ordered into canonical chronology in memory afterwards, leaving the stored `sortOrder` unchanged and adding the id as the tiebreak the SQL ordering left open. Second, a well-formed JSON body that is not an object (`null` included) reached a property read and surfaced as a 500; `parseShareInput` now takes `unknown` and returns `null` for a non-object body, so the route answers the existing `INVALID_SHARE` 400. The revoke route reads no body and needed no equivalent change. A third finding closed the neighbouring case: a body that is not valid JSON at all threw a `SyntaxError` out of `context.req.json()` before the route saw it, so the answer came from the global `onError` in `server/app.ts` as a generic `INVALID_JSON` 400 rather than from the route. The read now goes through `readShareInput`, which takes the read as a thunk, catches that `SyntaxError` and returns the same `null` the non-object case returns, so malformed, non-object and well-shaped-but-invalid bodies are indistinguishable to the client and all leave by the route's own `INVALID_SHARE` 400. The thunk keeps the route on Hono's cached `context.req.json()` behind the body-limit middleware while the unit test hands in a plain `Request`.
- **Follow-up:** Phase B (guest Journey DTO and scope-closed navigation), Phase C (share-scoped media read URL with a TTL capped by the remaining grant lifetime), Phases D/E (read-only viewer and owner share UI), Phase F (CFAA matrix and hardening). `/api/shared/*` currently shares the existing per-IP anonymous rate-limit budget; Phase C media reads should re-check that budget against #197 tempo-aware prefetch. Grant membership is deliberately immutable - changing a share set means creating a new link. Malformed JSON on `POST /api/shares` is fixed in this PR: `readShareInput` catches the `SyntaxError` from `context.req.json()` and the route answers `INVALID_SHARE` 400, covered at the route level by the integration suite. Only the repo-wide equivalent remains follow-up: `atlases`, `journeys` and `uploads` still let a malformed body reach the global handler, and that belongs in a single cross-route change rather than in this PR.
