# PR #281 - Record the enforced main-branch ruleset in the contributor workflow

- **Source head:** `4cd124582415e85e672cdb1709ec202c78baa00d`
- **Scope:** Issue #38. Documentation only. `CONTRIBUTING.md`'s `## Repository protection` section stated that `main` *should* require `verify`, `merge-readiness`, resolved conversations and pull requests "when GitHub branch protection or repository rulesets are available for the repository plan"; the ruleset `queue` (id `22196729`) has been active on `main` since 2026-09-03, so the section now states what is enforced and links the new `docs/repository-protection.md`. That file records the ruleset's parameters rule by rule, the two deliberately unchanged parameters (`strict_required_status_checks_policy: false` and `require_extra_approval_for_unattributed_changes: true`), the reason the `merge-ready` label reaches the merge button through the required `merge-readiness` status check rather than through the ruleset itself, the three `gh api` calls that re-verify the configuration, and why re-running the `ci` workflow while `merge-ready` is applied makes the readiness controller withdraw the sign-off. No workflow, ruleset, repository setting, source file or test is changed.
- **User-visible change:** None in the product. A contributor reading `CONTRIBUTING.md` now learns that the merge sequence is enforced rather than advisory, and that `main` answering `404 Branch not protected` on the classic branch-protection endpoint does not mean it is unprotected.
- **Review fixes:** Two review threads exist and both are resolved: deliberate probe threads opened on `docs/repository-protection.md` to observe `required_review_thread_resolution` against a live merge attempt, each answered with the captured refusal. The owner then reported a merge blocker — `merge-readiness` publishing `failure: ci / verify is missing` on a head whose `verify` reads `success` — and attributed it to a controller lookup defect. Refuted with timestamps rather than fixed: the `ci` re-run this feature used to reproduce a pending required check replaced the head's `verify` check-run, which completed at `14:05:06Z`, after both sign-off runs were created at `14:01:47Z` and `14:04:24Z`. The controller failed closed against a genuinely incomplete verification and needed no change. The lesson was added to `docs/repository-protection.md` instead, in `4cd1245`.
- **Follow-up:** Force-push and deletion of `main` are evidenced by the effective `non_fast_forward` and `deletion` rules only, not by a live probe: the probe for those would have to attempt the destructive act, and a probe whose failure mode is an unprotected `main` losing history is not a probe worth running. Nothing else outstanding.
- **Validation:** Locally `pnpm typecheck`, `git diff --check` and `node scripts/pr-history.mjs validate-all` (`./init.sh smoke`, EXIT=0). CI stays authoritative; the `ledger` lane validates this file and the `core` and `browser-qa` lanes cover code this PR does not touch. The enforcement claims in the new document were each read back from `GET /repos/U2SG/startrips/rulesets/22196729` and `GET /repos/U2SG/startrips/rules/branches/main` rather than from the GitHub UI.
