# PR #281 - Record the enforced main-branch ruleset in the contributor workflow

- **Source head:** `beac9634a3c31bfa063d30f221148f2b455ab3e2`
- **Scope:** Issue #38. Documentation plus one narrow fix to the readiness controller's `verify` lookup. `CONTRIBUTING.md`'s `## Repository protection` section stated that `main` *should* require `verify`, `merge-readiness`, resolved conversations and pull requests "when GitHub branch protection or repository rulesets are available for the repository plan"; the ruleset `queue` (id `22196729`) has been active on `main` since 2026-09-03, so the section now states what is enforced and links the new `docs/repository-protection.md`. That file records the ruleset's parameters rule by rule, the two deliberately unchanged parameters (`strict_required_status_checks_policy: false` and `require_extra_approval_for_unattributed_changes: true`), the reason the `merge-ready` label reaches the merge button through the required `merge-readiness` status check rather than through the ruleset itself, the three `gh api` calls that re-verify the configuration, and why re-running the `ci` workflow while `merge-ready` is applied makes the readiness controller withdraw the sign-off. `.github/workflows/merge-readiness.yml` reads the exact-head `verify` check-run across every page (`--paginate --slurp` with `per_page=100`) instead of the default single page of 30, and reports `absent`, `still queued` / `still in_progress`, a real failing conclusion and an API read failure as distinct states instead of collapsing all of them into `missing`. The gate itself is unchanged: anything other than `success` is still refused, the single controller and the ruleset are untouched, and no competing gate is added. No other source file, test or repository setting is changed.
- **User-visible change:** None in the product. A maintainer whose sign-off is refused now reads why — `ci / verify is still in_progress` rather than `ci / verify is missing`. A contributor reading `CONTRIBUTING.md` now learns that the merge sequence is enforced rather than advisory, and that `main` answering `404 Branch not protected` on the classic branch-protection endpoint does not mean it is unprotected.
- **Review fixes:** Two review threads exist and both are resolved: deliberate probe threads opened on `docs/repository-protection.md` to observe `required_review_thread_resolution` against a live merge attempt, each answered with the captured refusal. The owner then reported a merge blocker — `merge-readiness` publishing `failure: ci / verify is missing` on a head whose `verify` reads `success` — and attributed it to a controller lookup defect. Refuted with timestamps rather than fixed: the `ci` re-run this feature used to reproduce a pending required check replaced the head's `verify` check-run, which completed at `14:05:06Z`, after both sign-off runs were created at `14:01:47Z` and `14:04:24Z`. The controller failed closed against a genuinely incomplete verification and needed no change. The lesson was added to `docs/repository-protection.md` in `4cd1245`. The owner's acceptance for the owning fix was nevertheless right on its second point and is implemented in `5e486c1`: the head already carried 22 check-runs against a default page size of 30, so the unpaginated lookup was one busy head away from genuinely losing `verify`, and `.conclusion // "missing"` reported a merely-pending check in the same words as an absent one — which is what made a correct refusal read as a lookup defect. The two acceptance points that require applying `merge-ready` and capturing a successful squash merge are the owner's to perform; the loop never applies the label and never merges.
- **Follow-up:** A green `merge-readiness` on a head with `verify: success` is still unproven at runtime, because proving it requires a human to apply `merge-ready`. Force-push and deletion of `main` are evidenced by the effective `non_fast_forward` and `deletion` rules only, not by a live probe: the probe for those would have to attempt the destructive act, and a probe whose failure mode is an unprotected `main` losing history is not a probe worth running. Nothing else outstanding.
