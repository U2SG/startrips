# PR #236 - Drive the Journey Playback transport from the elapsed-time plan

- **Source head:** `db23db0f2a28348fc5a1a5e425e5603d49f7fe9f`
- **Scope:** #126 sections 3 and 4, the wiring only. `journeyPlaybackPlan.ts` gains `PlaybackStepDurationResolver` (the director re-exports it from its own module) and `resolvePlaybackStepDurationMs()`, the one place a beat becomes milliseconds; `buildPlaybackPlan(journey, tempo, resolveStepDuration?)` now emits exactly one segment per beat of `buildPlaybackSteps` at the same index and takes `meaningfulStepIndexes` from the shared scan, and its `nextMeaningfulStepIndex()` is a one-line delegation. `PlannedPlaybackSegment.sourceStepIndex` is dropped: with a 1:1 plan it always equalled `stepIndex` and had no consumers. `journeyPlayback.ts` replaces `nextMeaningfulPlaybackStepIndex` / `previousMeaningfulPlaybackStepIndex` with `meaningfulPlaybackStepIndexes()` plus one `meaningfulPlaybackStepIndex()` scan that `playbackReducer` calls directly for `next` and `previous`. `useJourneyPlaybackDirector.ts` resolves durations through the shared call, exposes `plan` (a `useMemo` over journey, tempo and resolver) and `getTimerBudget()`, and exports the pure `playbackProgressFraction()`. `JourneyPlaybackOverlay.tsx` positions the fill, the chapter ticks and the scrub range from the plan, drops `stepsProgress`, maps a scrub fraction through `playbackElapsedForFraction` and `playbackSegmentAtElapsed` to a step index, and animates the fill inside a beat with one CSS transition per beat. New cases in `journeyPlaybackPlan.test.ts`, `useJourneyPlaybackDirector.test.ts` and `journeyPlaybackNavigation.test.ts`. No value in `PLAYBACK_TEMPO_PROFILES` changed, no schema change, no server file touched.
- **User-visible change:** The playback progress bar is now time-weighted instead of step-weighted: the fill advances continuously inside a beat rather than jumping once per beat, a long video beat occupies as much of the bar as it occupies of the run, and the chapter ticks sit where those arrivals actually fall in time. Dragging the scrub bar picks the beat playing at that point in the planned run instead of an evenly spaced step, and the scrubber now announces an elapsed / total clock. Arrow keys on the focused scrubber still move one chapter. Under reduced motion the fill still moves once per beat, exactly as it did before.
- **Review fixes:** None yet; this is the first push of this PR.
- **Follow-up:** Journey-scoped media (`routePointId: null`) is not a beat of `buildPlaybackSteps`, so the plan no longer emits segments for it — the plan describes what actually plays. Whether the intro should play that media at all is a product question for the Playback V2 epic and is not decided here. The plan is not yet the source of the beats themselves: the director still drives `buildPlaybackSteps` and the plan is derived alongside it, so section 5B (spatial media handoff), section 6 (video duration policy, #195's area) and section 7 (soundtrack alignment) are untouched, as are the pacing values of ST-010 / ST-011. The scrub range remains a fraction of the plan rather than a real time input, so the thumb position updates per beat while the fill animates.
- **Validation:** Locally only `./init.sh smoke` — `pnpm typecheck` for the client and server projects, `git diff --check`, and `pr-history validate-all` / `validate-pr`. A captured `git diff origin/main -- src/journey/journeyPlaybackPlan.ts` evidences that no tempo profile value moved. No local test run, dev server, browser, database or Docker; CI is authoritative here and runs the full suite, the build and the browser QA lanes. Behaviour is pinned in the `core` lane: index and length parity between the plan and `buildPlaybackSteps` on a fixture that carries journey-scoped media; `plan.totalDurationMs` equal to the sum of `resolvePlaybackStepDurationMs` over every beat at `fast`, `standard` and `immersive`, both without a resolver and with an injected Quick Recap-style resolver that overrides one beat; `playbackProgressFraction` increasing strictly as a beat's budget drains, reaching exactly 1 on the last beat, staying inside its own beat when the live budget and the planned length disagree, and returning no `NaN` for a missing plan or an unknown beat; and the reducer and the plan answering identically for next and back at every step index.
