# PR #205 - Add shared narrative timing resolver

- **Source head:** `53790d34fe7e9cf2c1bca5efcfd06dcb3485c14e`
- **Scope:** Adds `src/journey/narrativeTiming.ts`, a pure module exporting `NarrativeMode` / `NarrativeTempo` / `NarrativeSegmentKind` / `NarrativeTimingContext` / `NarrativeTimingProfile`, the per-mode `NARRATIVE_TIMING_PROFILES` table, and `resolveNarrativeTiming()`, which returns an integer millisecond count `>= 0`. It is the single place that converts narrative context into a beat length, replacing the four independent timing truths the codebase holds today: `PLAYBACK_TEMPO_PROFILES` (`journeyPlaybackPlan.ts`), `IMAGE_DWELL_MS` / `VIDEO_DWELL_MS` / `CAMERA_MS` / `ARRIVAL_MS` (`autoEditPlan.ts`), Keepsake's desired durations, and the legacy `PLAYBACK_PACING` table (`journeyPlayback.ts`). Every profile row is seeded from the numbers that play today, each with a comment naming its source: the `full` rows are `PLAYBACK_TEMPO_PROFILES` verbatim with `imageRoleMs.representative` = that profile's `imageMs`; the `quick-recap` rows keep `IMAGE_DWELL_MS` / `VIDEO_DWELL_MS` and turn the flat `CAMERA_MS` (1000) and `ARRIVAL_MS` (800) into base values carrying Full Playback's distance and note slopes, per decision D2; the `keepsake` rows are `PLAYBACK_PACING` verbatim and identical across all three tempi, per decision D3. Target-duration budgeting stays outside the resolver by design - Quick Recap keeps its greedy selection loop and Keepsake keeps `fitKeepsakeSceneDurations()`. Two existing files change: `autoEditPlan.ts` gains an `export` on the four duration constants (no value or logic change) so the equivalence tests can assert against the originals rather than duplicate literals, and `useJourneyPlaybackDirector.ts` loses the dead `introMs` / `outroMs` return fields together with their now-orphaned `PLAYBACK_PACING` import.
- **User-visible change:** None. No caller is switched onto the resolver in this PR, so every rendered duration is byte-identical.
- **Review fixes:** None yet. Two findings were corrected before the commit. First, deleting the director's `introMs` / `outroMs` fields orphaned the `PLAYBACK_PACING` import in that file - a grep limited to the field names would not have shown it, and leaving it would have failed `typecheck` under `noUnusedLocals`; a `PLAYBACK_PACING` grep scoped to the one file confirmed lines 172-173 were its only uses. Second, the D2 assertion that a nearby Quick Recap leg "stays at the floor" was written as an exact equality and failed at `immersive`, where a 0.001 rad leg resolves to 1000.65 and rounds to 1001. The resolver was correct and the assertion was wrong, so the test now allows the one-millisecond rounding of a sub-millisecond distance term and asserts separately that a long-haul leg exceeds it - which is the actual D2 property.
- **Follow-up:** PR 2 (#166 validator re-scope) must delete the four now-exported constants and remove the four millisecond equalities in `validateAutoEditPlanV1`, and should deliberately confirm one divergence: a video whose intrinsic duration is absent or non-positive resolves to `videoMs`, where `autoEditPlan`'s `itemDuration()` returns `0`. That divergence is latent rather than live, because #202 makes Quick Recap always emit an explicit pending video duration, so no digest reaches the resolver without one today. PR 4 (Quick Recap tempo wiring) must re-check the greedy budget's `baseOverhead`, which assumes a flat `CAMERA_MS + ARRIVAL_MS` per route point: a long-haul leg can now exceed that, so the plan's own §7 prediction that the Full Playback fallback rate will move applies to that PR. Quick Recap's intro/outro were seeded from `PLAYBACK_TEMPO_PROFILES` rather than the legacy `PLAYBACK_PACING`, because the former is what the director actually spends for those two beats; correcting `quickRecapPlayback.ts`'s 3000 ms budget subtraction is PR 4's job. PRs 3, 5 and 6 are unchanged from the plan.
