# PR #402 - Execution guard verifies its own identity on MSYS

- **Source head:** `1b35d77b1bc86c995df00775a1b325c12a8f5eb4`
- **Scope:** Control-plane distribution only: the duplicate-execution guard and the identity it verifies, the supervisor that publishes that identity and stops on a deterministic self-block, the test module's import resolution, real startup-chain and classification regressions, python bytecode ignores, and the control-plane workflow's shell syntax checks. No application, server or product source changes.
- **User-visible change:** A local Windows worker can start again. Since the previous distribution was activated, every run-loop iteration reported the supervisor that had just launched it as a competing execution and exited rc=6, so the supervisor retried on a ten-minute timer and the loop produced nothing while appearing alive. A repeat of that self-block now stops in one iteration instead of twelve hours, and a process whose command line the provider cannot read no longer blocks a start merely because some other session owns it. Behavior off MSYS is unchanged.
- **Review fixes:** Addressed review comment 4034197293. The first revision exempted a published pid, and any direct child of one, before reading the command line, the workspace or the carrier kind; since Windows reuses process ids, that could later have hidden a genuinely competing execution. Publication now carries pid bound to its observed start stamp, the exemption happens only after classification and only on a matching stamp, and the child exemption was removed; an unreadable command line reaches no exemption at all, preserving the UNKNOWN established by #400. A second review pass found the startup regression proved less than it claimed: it stood in for `run-loop.sh`, its normal case never required the guard to succeed, and nothing exercised the new self-block branch. The normal case now runs the distributed `run-loop.sh` with `gh` as the only stand-in and asserts guard success, permission success, reconcile, intake and the selection point; a probe covers the supervisor's own branches. The import regression was likewise rewritten: `find_spec()` answers from `sys.modules` for an already-imported name, so it now plants a shadowing copy and asks a real spawned interpreter.
- **Follow-up:** The procfs provider turns a single unreadable process under `/proc` into `EvidenceUnknown` for the whole observation, so the real startup chain cannot complete on the Linux runner and those cases are scoped to Windows, where the ancestry break actually occurs. Pre-existing and untouched here. The local workspace still runs an earlier distribution carrying an equivalent fix by hand; eleven distributed files differ and three are absent there, so a normal activation, not this merge, is what updates it. `test_actual_parallel_processes_keep_both_updates` failed once under load on its ten-second barrier and passed in isolation and on rerun; pre-existing flakiness, untouched.
- **Validation:** Exact Source 1b35d77b1bc86c995df00775a1b325c12a8f5eb4: control-plane CI 35203806271 passed on ubuntu-latest and windows-latest, 243 tests, with the Windows runner recording each chain case individually as ok and Linux skipping the three Windows-scoped classes. The MSYS ancestry break was first reproduced directly, printing the ppid chain the guard walks and showing it end at an exited stub below the supervisor. The distributed `run-loop.sh` then ran through the real launcher and supervisor to rc=0 at its selection point; separate probes proved a refusal names our live chain and a self-block exits 8 without spending the transient budget. Synthetic cases cover the severed chain, the verified identity, the reused stamp, the bare pid, a child under a published parent, an unreadable command line, and unreadable processes under foreign, own-workspace and worker-marker parents. The shadowing fix was verified with the stale copy still present, so the fix and not its removal does the work.
