# PR #402 - Execution guard verifies its own identity on MSYS

- **Source head:** `e9949ceb1692c06c9cf0f73ade0d03b8104e7aca`
- **Scope:** Control-plane distribution only: the duplicate-execution guard and the identity it verifies, the supervisor that publishes that identity and stops on a deterministic self-block, the test module's import resolution, the real startup-chain and classification regressions, python bytecode ignores, and the control-plane workflow's shell syntax checks. No application, server or product source changes.
- **User-visible change:** A local Windows worker can start again. Since the previous distribution was activated, every run-loop iteration reported the supervisor that had just launched it as a competing execution and exited rc=6, so the supervisor retried on a ten-minute timer and the loop produced nothing while appearing alive. A repeat of that self-block now stops in one iteration instead of twelve hours. Behavior off MSYS is unchanged.
- **Review fixes:** Addressed review comment 4034197293. The first revision exempted a published pid, and any direct child of one, before reading the command line, the workspace or the carrier kind; since Windows reuses process ids, that could later have hidden a genuinely competing execution. Publication now carries pid bound to its observed start stamp, the exemption happens only after classification and only on a matching stamp, and the child exemption was removed. An unreadable command line no longer reaches an exemption at all, preserving the UNKNOWN established by #400. The import regression was rewritten after review: `find_spec()` answers from `sys.modules` for an already-imported name, so it proved nothing; it now plants a shadowing copy and asks a real spawned interpreter.
- **Follow-up:** The procfs provider turns a single unreadable process under `/proc` into `EvidenceUnknown` for the whole observation, so the real startup chain cannot complete on the Linux runner and those cases are scoped to Windows, where the ancestry break actually occurs. Pre-existing and untouched here. The local workspace still runs an earlier distribution carrying an equivalent fix by hand; a normal activation supersedes it. `test_actual_parallel_processes_keep_both_updates` failed once under load on its ten-second barrier and passed in isolation and on rerun; pre-existing flakiness, untouched.
- **Validation:** Exact Source e9949ceb1692c06c9cf0f73ade0d03b8104e7aca: control-plane CI 35199586348 passed on both ubuntu-latest and windows-latest, Windows reporting OK and Linux OK (skipped=3) for the Windows-scoped chain cases. The MSYS ancestry break was first reproduced directly, printing the ppid chain the guard walks and showing it end at an exited stub below the supervisor. The startup chain then ran as real processes on the Windows runner -- launcher, supervisor, run-loop and guard, with only the model and GitHub work stood in -- proving that our own chain is not blocked by itself, that a second launch is refused and names our live supervisor, and that a published number whose stamp no longer matches stays UNKNOWN. Synthetic cases cover the severed chain, the verified identity, the reused stamp, the bare pid, a child under a published parent and an unreadable command line. The shadowing fix was verified with the stale copy still present, so the fix and not its removal does the work. This final adds only this ledger.
