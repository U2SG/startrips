# PR #612 - Keep Story and Journey Playback on one grouped-chapter order

- **Source head:** `fed1c9dc5124d3719b64cfd11deae7ef62494e51`
- **Scope:** Issue #76, acceptance criterion "Story and Cinematic Journey Playback share the same chapter/media ordering semantics" - **one of the #76 problems only; #76 stays open after this PR.** A Route Point grouped into a Stop (`stayAnchorRoutePointId`) has its media folded into that Stop's chapter, so one chapter can mix several Route Points. `playbackMediaByChapter` ordered that merged chapter by `sortOrder` alone (`src/journey/journeyPlayback.ts:133` before the change), but `sortOrder` is a Journey-global upload counter assigned `max + 1` at upload (`server/services/multipart-uploads.ts:181-199`) and renumbered `0..n-1` only on an explicit reorder (`server/repositories/media-order.ts:25-31`). A group's child media could therefore sort ahead of the media of the Stop that owns the chapter. Canonical route position now decides first and `sortOrder` only orders media inside one Route Point (`src/journey/journeyPlayback.ts:134-148`), so the folded chapter agrees with the per-owner route order by construction.
- **User-visible change:** None intended. This removes a disagreement between two surfaces rather than adding behaviour: for a journey containing a grouped Route Point, Story's whole-Journey playthrough and Cinematic Journey Playback previously showed the same assets in a different order depending on which surface the member was in. They now tell the same story in the same sequence.
- **Review fixes:** The defect was reproduced by execution before it was reported, not inferred from reading. Route points A (Stop), C (grouped under A), B (Stop) with media c1->C sortOrder 0, a1->A sortOrder 1, a2->A sortOrder 2 yielded Story ["a-1","a-2","via-1"] against Playback ["via-1","a-1","a-2"]. The state is reachable because Story's organizer always resends the whole visual list (`JourneyStory.tsx:3585-3600`), so any manual reorder makes the two orders agree again and the defect hides. It was never covered because every point helper in the existing #76 tests is `isStop: true` (`journeyPlayback.test.ts:29-46`), which exercises only the all-Stop fast path at `journeyPlayback.ts:114-117` where a chapter has exactly one owner and the defect cannot exist. The all-Stop path and `playbackStoryMedia` were both deliberately left untouched: the first because a route-index sort key is a no-op there, the second because keepsake narrative snapshots read it (`journeyKeepsake.ts:121`) and changing it would invalidate existing keepsakes.
- **Follow-up:** **#76 remains open; this PR fixes only the grouped-chapter ordering disagreement and does not close the issue.** The owner's clarification of 2026-09-28 on #76 supersedes the earlier Story scope/terminal wording: in normal Story viewing a selected Route Point is a chapter/jump position, not a hard media boundary, and `selectedRoutePointId` truncating `scopedMedia` so that each Route Point becomes an island that loops on itself is a P1 regression still to be fixed. Consequently the point-scoped `storyMediaForScope(anchorId)` behaviour is **not** recorded here as deliberate or accepted design; it is part of that open regression, and point-only scoping survives only in an explicit management/filter mode. The same clarification also supersedes the earlier "no implicit wrap" wording: whole-Journey autoplay is to loop at the Journey boundary back to the first playable media rather than stop at the last one, so the existing `hold-terminal` branch (`JourneyStory.tsx:2134-2135`, `storyMediaPolicy.ts:179-189`) is also part of that open work and is untouched here. Separately, the active-chapter highlight (`JourneyStory.tsx:3984`, `is-chapter-active`) still has no test coverage repository-wide.
