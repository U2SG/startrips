# PR #282 - Read the exact-head verify check across all pages and name its real state

- **Source head:** `0f4496d3560e4a2f99f0ad67d63a0f4827a2b0a3`
- **Scope:** Issue #38, follow-up to #281, which merged before this could land in it. `.github/workflows/merge-readiness.yml` resolved `ci / verify` with a single unpaginated `GET /commits/{sha}/check-runs` and `.conclusion // "missing"`. The lookup now pages the head's check-runs with `--paginate --slurp` and `per_page=100`, and reports `absent`, `still queued` / `still in_progress`, the real failing conclusion, and an API read failure as distinct states. The default page holds 30 check-runs and #281's head already carried 22, so a head whose CI has been re-run was one busy round away from losing `verify` behind page one; separately, a still-running check has `conclusion: null` and was reported with the same word as an absent one, which is what made a correct fail-closed refusal read as a lookup defect on #281. `docs/repository-protection.md` is updated to match the new wording. The gate is unchanged: anything other than `success` is still refused, the label is still withdrawn, the single controller and the ruleset are untouched, and no competing gate is added.
- **User-visible change:** None in the product. A maintainer whose sign-off is refused now reads why — `ci / verify is still in_progress` rather than `ci / verify is missing`.
- **Review fixes:** None at the time of writing.
- **Follow-up:** A green `merge-readiness` produced by an actual `merge-ready` on a head with `verify: success` is still unproven at runtime, because proving it requires a human to apply the label. That, and capturing a successful squash merge behind it, are the two remaining points of the owner's acceptance on #38 and are the owner's to perform.
- **Validation:** Locally `pnpm typecheck`, `git diff --check` and `node scripts/pr-history.mjs validate-all` (`./init.sh smoke`, EXIT=0), a YAML parse of the changed workflow, and the new state expression evaluated against three real heads' paginated check-run payloads — `89f6a40` with 17 check-runs, `8e5bbdc` with 22 and `88ed38a` with 14, all resolving to `success`, so the gate verdict is unchanged where it matters. CI stays authoritative, and this workflow's own behaviour is exercised by the readiness run on this PR.
