# PR #210 - Drive Quick Recap timing from the runtime tempo

- **Source head:** `a350ea0f6996f3af575131c62354befd84bb2b4d`
- **Scope:** `quickRecapStepDurationMs()` in `src/journey/quickRecapPlayback.ts` gains a `tempo` argument and resolves travel and arrival through `resolveNarrativeTiming({ mode: "quick-recap", ... })` with `routePointAngularDistance()` and the trimmed note length, instead of reading the frozen plan's flat camera and arrival milliseconds; media dwell stays pinned by the plan, with the resolver only supplying a dwell the plan left unpinned. `prepareQuickRecapPlaybackResult()` budgets the chapter target against the resolver's per-tempo intro/outro rather than legacy `PLAYBACK_PACING`'s flat 1200 + 1800. `PlaybackStepDurationResolver` widens to `(journey, step, tempo)` and `useJourneyPlaybackDirector` passes its own tempo at the call site (tempo ownership option (a); tempo state is not lifted into `LivingAtlasApp`), exporting `PLAYBACK_INITIAL_TEMPO` so the opening plan is budgeted at the tempo the run starts in. The director's `stepKey` drops the resolved duration. `JourneyPlaybackOverlay` gains an `onTempoChange` prop and `LivingAtlasApp` rebuilds the Edit Plan from the source journey on a tempo change (decision D1); new pure helpers `playbackStepIdentity()` / `remapPlaybackStepIndex()` map the playing step across that rebuild. Reverts #206: `playbackTempoControlVisible()`, its test and the two quick-recap grid overrides in `src/styles/journey-playback.css` are removed and the tempo control renders in both modes. PR 4 of the shared narrative timing plan (#126, #166, #197).
- **User-visible change:** The Playback tempo control is visible again in Quick Recap and now changes the whole recap, not just its intro and outro: a tempo change re-plans selection and durations against the same ~45 s target, and a nearby leg is no longer paced like an intercontinental one. In Full Playback a tempo change now scales the current beat's remaining time instead of restarting that beat.
- **Review fixes:** None yet.
- **Follow-up:** The planner's greedy budget in `autoEditPlan.ts` (out of scope here) books a flat `travelBase` + `arrivalBase` per route point because route geometry and notes are not part of the deterministic plan input, while playback now spends the distance- and note-aware value, so runtime exceeds `plannedDurationMs` with no gate noticing - measured on a 5-city intercontinental fixture (HKG-LHR-JFK-NRT-SYD, ~30-character note per stop, 3 photos each): planned 40700 ms vs runtime 45175 ms at `standard` (+4475 ms), +3093 ms at `fast`, +6048 ms at `immersive`. This does not make `over-budget` trip more often, since the planner cannot see the distance; what moves the fallback rate is the intro/outro budget fix, which changes the chapter budget from a flat 42000 ms to 43200 / 42400 / 41600 ms. A rebuild that no longer fits the budget keeps the plan that is playing, so that one tempo has no visible effect rather than dropping the viewer into Full Playback mid-recap. Remaining `PLAYBACK_PACING` / `stepDurationMs` consumers for PR 6: `journeyPlayback.ts` itself, `journeyPlayback.test.ts:82-91, 311-322`, `narrativeTiming.test.ts:322-334`, and `quickRecapPlayback.ts:27` (`QUICK_RECAP_PENDING_VIDEO_DURATION_MS = PLAYBACK_PACING.videoMs`), which the plan's PR 6 paragraph does not list; there is no other production consumer of `stepDurationMs`.
