# PR #210 - Drive Quick Recap timing from the runtime tempo

- **Source head:** `3bdd82e38630eeee119a03a1e33a7c7b842a7b42`
- **Scope:** `quickRecapStepDurationMs()` in `src/journey/quickRecapPlayback.ts` gains a `tempo` argument and resolves travel and arrival through `resolveNarrativeTiming({ mode: "quick-recap", ... })` with `routePointAngularDistance()` and the trimmed note length, instead of reading the frozen plan's flat camera and arrival milliseconds; media dwell stays pinned by the plan, with the resolver only supplying a dwell the plan left unpinned. `prepareQuickRecapPlaybackResult()` budgets the chapter target against the resolver's per-tempo intro/outro rather than legacy `PLAYBACK_PACING`'s flat 1200 + 1800. `PlaybackStepDurationResolver` widens to `(journey, step, tempo)` and `useJourneyPlaybackDirector` passes its own tempo at the call site (tempo ownership option (a); tempo state is not lifted into `LivingAtlasApp`), exporting `PLAYBACK_INITIAL_TEMPO` so the opening plan is budgeted at the tempo the run starts in. The director's `stepKey` drops the resolved duration. `JourneyPlaybackOverlay` gains an `onTempoChange` prop and `LivingAtlasApp` rebuilds the Edit Plan from the source journey on a tempo change (decision D1); new pure helpers `playbackStepIdentity()` / `remapPlaybackStepIndex()` map the playing step across that rebuild. Reverts #206: `playbackTempoControlVisible()`, its test and the two quick-recap grid overrides in `src/styles/journey-playback.css` are removed and the tempo control renders in both modes. PR 4 of the shared narrative timing plan (#126, #166, #197).
- **User-visible change:** The Playback tempo control is visible again in Quick Recap and now changes the whole recap, not just its intro and outro: a tempo change re-plans selection and durations against the same ~45 s target, and a nearby leg is no longer paced like an intercontinental one. In Full Playback a tempo change now scales the current beat's remaining time instead of restarting that beat.
- **Review fixes:** Codex review (comment 3930654984) found that a tempo rebuild which adds or drops beats ahead of the playing one restarted the current image: the overlay remaps the surviving beat to its new step index with a `seek()`, and the timer's `stepKey` still carried `state.stepIndex`, so the remap took the reset branch and restored the beat's full duration. `3bdd82e` keys the timer by the beat's narrative identity (`${journey.id}:${playbackStepIdentity(journey, step)}`) and adds the pure `resolvePlaybackTimerBudget()`, which owns the reset / replan / resume decision. Identity alone is not enough: the rebuild and the remapping `seek()` land in two separate commits, and in the one between them the director still holds the old index - now addressing a different beat - so the live budget is parked in a one-slot carry tagged with its own identity and claimed when the seek arrives. Only a rebuild remap may claim it (`seek(index, { carryProgress: true })` from the overlay's remap effect); a user seek from the scrubber restarts the beat it lands on, and a beat the rebuild deleted starts fresh on its neighbour. `PLAYBACK_TEMPO_PROFILES` and Full Playback behaviour are untouched. `playbackStepIdentity()` moves from `quickRecapPlayback.ts` to `journeyPlayback.ts`, next to the `playbackMediaForPoint()` it calls, so the generic director does not import the Quick Recap module.
- **Follow-up:** The planner's greedy budget in `autoEditPlan.ts` (out of scope here) books a flat `travelBase` + `arrivalBase` per route point because route geometry and notes are not part of the deterministic plan input, while playback now spends the distance- and note-aware value, so runtime exceeds `plannedDurationMs` with no gate noticing - measured on a 5-city intercontinental fixture (HKG-LHR-JFK-NRT-SYD, ~30-character note per stop, 3 photos each): planned 40700 ms vs runtime 45175 ms at `standard` (+4475 ms), +3093 ms at `fast`, +6048 ms at `immersive`. This does not make `over-budget` trip more often, since the planner cannot see the distance; what moves the fallback rate is the intro/outro budget fix, which changes the chapter budget from a flat 42000 ms to 43200 / 42400 / 41600 ms. Elapsed fraction now survives a rebuild that moves the playing beat (see Review fixes), so plan section 7's "elapsed fraction does not survive a selection change" holds only for a beat the rebuild actually deletes. `QUICK_RECAP_PROFILES` (#205) seeds `travelBaseMs: 1000` identically at all three tempi and varies only the per-radian slope, so a `nearby` leg at the plan's own 6-degree threshold resolves to 1031 / 1047 / 1068 ms and a 1-degree leg to 1005 / 1008 / 1011 ms, against 1288 / 1432 / 1624 ms for a 55-degree leg - a same-city recap gets almost no camera response to the tempo control, and giving the quick-recap profile a per-tempo travel floor is a product decision rather than a wiring fix. A rebuild that no longer fits the budget keeps the plan that is playing, so that one tempo has no visible effect rather than dropping the viewer into Full Playback mid-recap. Remaining `PLAYBACK_PACING` / `stepDurationMs` consumers for PR 6: `journeyPlayback.ts` itself, `journeyPlayback.test.ts:82-91, 311-322`, `narrativeTiming.test.ts:322-334`, and `quickRecapPlayback.ts:27` (`QUICK_RECAP_PENDING_VIDEO_DURATION_MS = PLAYBACK_PACING.videoMs`), which the plan's PR 6 paragraph does not list; there is no other production consumer of `stepDurationMs`.
