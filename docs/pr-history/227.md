# PR #227 - Move immersive media viewing into mobile Viewer mode

- **Source head:** `835dddf4f85ac61fa929fb1c164aee9feefcef5f`
- **Scope:** Follow-up to the closed #199. `src/journey/JourneyStory.tsx` gains an exported `showMobileStoryFullscreenControl` gate and a `journey-story__mobile-media-fullscreen` `IconActionButton` in the mobile Viewer action cluster, and loses the `沉浸播放` / `沉浸查看` button from the media management sheet. The play-control gate is hoisted into `mobileStoryPlayControlVisible` so the immersive entry can take the playback slot (`is-compact`) when a single-asset scope renders no play control. New exported `storyImmersiveEntryKeepsPlaying(playing, candidate, availability)` decides whether the entry carries the sequence into fullscreen. `src/styles/living-atlas.css` extends the two-slot cluster rules to three slots plus the compact variant. `src/journey/JourneyStory.test.ts` adds the two predicate suites and an SSR case for the rendered row; `scripts/qa-media-controls.mjs` grades the entry at four phone widths, adds `story-mobile-viewer-immersive-entry-video`, and adds `story-mobile-manage-sheet-has-no-playback`, which scans the sheet's real buttons rather than one known label. No schema change, no server file touched, no migration and no regenerated `server/db/auth-schema.ts`.
- **User-visible change:** On a phone, immersive viewing now has its own control in the Story viewer, next to play/pause, and works when the current asset is a video — previously the only entry for a video was inside the media management sheet, because the inline tap-to-open path is bound to the image element. The sheet no longer offers `沉浸播放` / `沉浸查看`; it keeps cover, ordering, reclassification and deletion. Entering and leaving fullscreen no longer stops a running sequence from this control, and a single-asset scope keeps its immersive entry without being offered sequence autoplay.
- **Review fixes:** Codex raised one P2, valid: with `playing` already true, `enterFullscreen(true)` reaches `setPlayingFromGesture(true, "fullscreen")`, which returns early while the next video candidate's signed read is `waiting`, so the fullscreen `<video>` never receives the gesture-authorized `play()` while the overlay still opens and `playing` stays true — on a browser with per-element autoplay restrictions the later passive `play()` can be refused and the step degrades to the slide timer. `e5eeef1` conditions the handoff on the same `storyAutoplayCanStart` rule instead of disabling the control: blocking immersive viewing on a transient read would reintroduce exactly the discoverability failure #199 is about, and viewing does not depend on that read. `error` still carries playback, because a failed read is terminal for that step and the existing timer policy owns it. The owner then blocked the head on two CI failures. `browser-qa / login-media` was diagnosed before any code was touched: mobile fullscreen opens immersive with `is-controls-hidden` by design, so `.journey-story-fullscreen__close` resolves but is not visible, and the new case wrongly reached for it; `835dddf` leaves through `window.history.back()`, the exit path this lane already covers, and asserts `enteredImmersive` so the state that hid the button is graded rather than worked around. The missing ledger is this file.
- **Follow-up:** The photo-tap path keeps `enterFullscreen(false)`, so tapping the image while a sequence plays still stops it; that gesture is disambiguated from swipe rather than an explicit request, and changing it is outside this feature. Tapping a video still does not open fullscreen — the native control strip owns that surface — which the new entry makes moot for reachability but does not unify. Three controls now share the cluster row, so a fourth would need a placement decision rather than another slot.
