# PR #673 - Park the soundtrack ducking loop once the gain arrives

- **Source head:** `10d80a6b504b89d8511d9b74cb54e25579e9d32a`
- **Scope:** `soundtrackDuckingController` polls per frame only while a ramp is in flight or on the frame after a watched change (foreground element, media generation, soundtrack element, external level, duck decision); otherwise it parks on an idle tick that reads the same live state. New injectable `setIdleTimer`/`cancelIdleTimer` host hooks mirror `requestFrame`/`cancelFrame`; outside a browser the default idle path routes through the host's `requestFrame`, so the loop cannot die. The pending tick records its kind, so `stop()` cancels through the matching call. The idle interval is derived in shared policy: `SOUNDTRACK_DUCK_ATTACK_WINDOW_MS` (300, #596's ceiling) minus `SOUNDTRACK_DUCK_ATTACK_MS` (220) minus one frame of margin, i.e. 63 ms, so idle detection plus attack stays within the window. Unit tests drive both scheduling paths explicitly with disjoint handles (parking, waking on pause/mute/end/new video/replaced soundtrack/external level/generation, `stop()` while parked and while ramping, the non-browser default), assert the constant bounds, and prove a worst-case event-less video start reaches the duck target within 300 ms.
- **User-visible change:** None intended. A photo-only Journey no longer keeps a per-frame loop; a transport change that raises no event is picked up within one idle tick, still inside the #596 attack window.
- **Review fixes:** Codex P2 (thread PRRT_kwDOT1Guu86poPtf) in 10d80a6b: the original 150 ms idle tick plus the 220 ms attack could take about 370 ms to duck; the tick is now bounded by the attack window.
