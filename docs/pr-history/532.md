# PR #532 - Spend a Google sign-in id token exactly once

- **Source head:** `f57759f092e98958a05c255153e86341e85bc9e2`
- **Scope:** Add a `verifyIdToken` override to `googleSignInOptions` in `server/account-identities/social-providers.ts`: it delegates to a base adapter built without the override, forwards the caller's `nonce`, and then spends the token through the shared `consumeVerifiedIdToken` store, so the direct `idToken` body on `/api/auth/sign-in/social` stops treating Google's audience check as replay protection. No new infrastructure - the provider-keyed `provider_id_token_consumptions` table, its digest key and its pruning all arrived with #350; this reuses the exact shape `apple-provider.ts` took under that owner decision B. Six cases were added to `server/tests/account-identity-google.integration.test.ts`, the file that owns the pre-import `GOOGLE_CLIENT_ID`, the RS256 keypair and the JWKS/token `fetch` stub.
- **User-visible change:** A Google id token now signs a user in once. A second presentation of the same token is refused with 401 instead of minting another session; a browser authorization-code sign-in, an explicit #349 bind and a token refresh are all unaffected, because none of them reaches the override.
- **Review fixes:** None. The independent Source review of `f57759f` returned CLEAR with no findings, and no review round moved the code.
- **Follow-up:** None. The regression family is "paths where provider verification is mistaken for replay protection"; `configuredSocialProviderIds` is exactly `{google, apple}`, Apple was closed by #350 and Google is closed here, and the only other `verifyIdToken` caller in the pinned library is `/link-social`, which is listed in `STARTRIPS_DISABLED_IDENTITY_PATHS` with `accountLinking.enabled` false. No sibling defect of this class remains, so no new issue was filed. Two inherent behaviours are recorded rather than changed: a token is spent at verification, so a presentation that then fails `disableImplicitSignUp` must be retried with a fresh token, and the fail-closed store-outage path stays covered by #350's Apple suite rather than being re-proven from a second file.
- **Validation:** Exact Source CI on `f57759f` passed `core`, `keepsake-render` and all nine `browser-qa` lanes; `ledger` and `verify` were the expected pre-ledger failures that this ledger commit closes. Locally `./init.sh smoke` was EXIT=0 on that head - `pnpm typecheck` clean on both projects, `git diff --check` clean, `node scripts/pr-history.mjs validate-all` over 188 files. Every test runs in GitHub Actions only; the six new cases are delegated to the `core` lane and no suite was run on this machine.
