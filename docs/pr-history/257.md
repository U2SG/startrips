- **Scope:** `src/journey/LivingAtlasApp.tsx` exports `showsGlobeModeChrome` and `atlasCinematicIsolationActive`; the first drives the globe's `showControls` input so `.living-atlas-globe__controls` / `.living-atlas-globe__mode` leave the DOM in globe focus mode, the second is the one expression the single `setCinematicIsolation(...)` call site passes, covering playback and focus mode together. New `scripts/qa-globe-focus-chrome.mjs`, registered as `qa:globe-focus-chrome` and as the `browser-qa / globe-focus-chrome` CI lane. `src/auth/AuthGateway.tsx` needed no change: `.account-dock` already carried `inert` + `aria-hidden` under cinematic isolation.
- **User-visible change:** In desktop globe focus mode the `深入真实地图 / REGION MAP` block and the account dock are gone from the screen and from the tab order, the top right is empty, and the only persistent control is a quiet top-left `返回图谱` that exits in one click; Escape still exits. Scrolling to zoom inside focus mode no longer dives into the detail map, so the mode cannot acquire MapLibre's own navigation and attribution controls; entering focus mode while that map is already up returns to the particle earth. Ordinary Atlas keeps its zoom-driven dive and its fallback control, and its selected Journey, timeline position and globe orientation survive the round trip.

## Cross-feature assumption audit

**Changed dimension: chrome and focus-tree ownership became variable per Atlas mode.** Whether `.living-atlas-globe__controls` exists, whether the account dock is in the accessibility tree, whether `.living-atlas-globe__mode-note` is permanent, and whether the detail surface may be composed at all are now all functions of `globeFocusMode`. Every subsystem that previously read them as fixed was checked:

- **Semantic Earth Dive (#252 / #259).** The invalidated assumption is that surface: `resolveEarthDive` assumed the detail surface is always a legal destination, and after #259 it reaches it from the zoom authority with no command at all. Focus mode renders a `SCROLL TO ZOOM` hint, so the mode's own guidance was a path into chrome the mode forbids. Suspension is an input to the resolver rather than a guard in the component, so the "one resolver decides" contract still holds; ownership, the one-step progression and the readiness gate are unchanged.
- **Playback cinematic isolation.** `setCinematicIsolation` had one writer and one reason. It now has one writer and two reasons through a single derived expression, so exiting playback while still in focus mode cannot restore the dock — checked as the ordering case that a two-call-site version would have got wrong.
- **Globe pick flow.** `onPickRequest` is rendered by `LivingAtlasGlobeControls`, which focus mode removes. Verified the pick path is only offered in detail mode, which focus mode now cannot reach, so no entry point is stranded.
- **`scripts/qa-post-login-controls.mjs`.** Holds the pre-existing `globe-focus exit contract` assertions. The control's marker class and render condition are unchanged — only its anchor, icon and accessible name moved — so that lane is untouched and still grades the same contract.
- **Mobile compact layout.** `showsGlobeModeChrome` keeps the existing `!isMobileV2` term, so compact mobile, which never rendered the mode chrome, is unaffected; #250/ST-035's mobile inert fix and the mobile `真实地图` action are not touched. The new 125% pass asserts it did not land in the compact composition.
- **DPR (#243).** The zoom pass emulates browser zoom, not device pixel ratio, and says so: `deviceScaleFactor` alone changes device pixels per CSS pixel and leaves layout identical, so the pass divides the CSS viewport as well.

**Regression-family search:** the failed assumption is "the detail surface is a legal destination in any Atlas mode". Its confirmed sibling is the zoom-driven dive entry described above, which is live on `main` after #259 and reachable inside focus mode without any command; it is the same class as the reported command-driven symptom and trivially in scope, so it is fixed in this PR rather than filed. The other subsystems that consume the same assumption were enumerated and checked: the fallback command path (covered by the same `suspended` precedence), the focus-revision staleness path in `resolveEarthDive` (unaffected — suspension resolves before it), and `applyDetailedEarthFocus`'s `Math.max(map.getZoom(), DETAILED_EARTH_INITIAL_ZOOM)` overshoot, which is a calibration defect rather than a chrome-ownership one and is already recorded in the #259 ledger's `Follow-up`. No new issue was warranted.
