# PR #313 - Verify stored media content identity

- **Issue relationship:** `Addresses #311` — ST-059 establishes the Backend/upload trust boundary that ST-058 / PR #310 requires before Quick Recap may treat a content hash as exact duplicate identity.
- **Source head:** `fefbef5d4df0d83b0f93f53f242b9b23c017f422`
- **Scope:** Add an explicit `media_assets.content_hash_verified` provenance bit through generated migration 0017 (historical rows default false); extend `MultipartStorage` with durable-object SHA-256 derivation; stream S3-compatible object bytes through Node SHA-256 without buffering whole media; require normal completion, completion recovery and stale-upload reconciliation to obtain the durable-byte hash before database finalization; make dedupe consult only verified hashes while preserving Journey + Route Point + media-kind scope. Guest/share projections remain unchanged and continue excluding storage identity/provenance.
- **User-visible change:** A forged, stale or faulty client-declared hash can no longer collapse different stored media into one asset. Exact duplicate identity now comes from the object that actually landed in storage. Upload completion performs one bounded-memory streaming read of the durable object, trading additional completion latency/storage bandwidth for authoritative identity without loading an up-to-2GB object into memory.
