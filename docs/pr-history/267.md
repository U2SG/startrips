# PR #267 - Refuse an unusable JSON body inside each route instead of the global handler

- **Source head:** `1b7e7fc5a198fac58960a95c86bd267bdc8eaae5`
- **Scope:** The follow-up recorded in PR #207's ledger. `POST /api/shares` already answered a malformed body with its own `INVALID_SHARE` 400 through `readShareInput`; `atlases`, `journeys` and `uploads` still let the `SyntaxError` from `context.req.json()` reach the global `onError` and leave as a generic `INVALID_JSON`. A new `server/routes/json-body.ts` exports `readJsonObject(read)`: it takes the body read as a thunk, so a route keeps Hono's cached `context.req.json()` behind the body-limit middleware while `server/routes/json-body.test.ts` hands in a plain `Request`; it catches the `SyntaxError`; and it answers the same `null` for a well-formed body that is not an object - `null`, a number, a string and an array included. All ten JSON-accepting routes on those three modules now guard the body before any property is read: `POST /api/atlases/bootstrap` and `PATCH /api/atlases/current` (`INVALID_ATLAS`), `POST /api/journeys` and `PATCH /api/journeys/:id` (`INVALID_JOURNEY`), `PATCH /api/journeys/:id/cover` (`INVALID_COVER`), `POST /api/uploads/start` (`INVALID_UPLOAD`), `POST /api/uploads/:id/complete` (`INVALID_UPLOAD_PARTS`), `POST /api/uploads/assets/reorder` (`INVALID_MEDIA_ORDER`), `POST /api/uploads/assets/move` (`INVALID_MEDIA_MOVE`) and `POST /api/uploads/assets/move/undo` (`INVALID_MEDIA_MOVE_UNDO`). Arrays are refused with the other non-objects because every parser here reads named properties, which an array reports as `undefined`. The parse functions keep their existing signatures and their existing 400 envelopes; the guard is two lines in front of each. The `onError` `INVALID_JSON` branch is unchanged and stays the backstop, with its comment extended to name what still reaches it. `shares.ts` is deliberately untouched.
- **User-visible change:** A client that sends an unusable body to any of those ten endpoints now gets that endpoint's own 400 code rather than a generic `INVALID_JSON`, and cannot tell a malformed body from a non-object one or from a well-shaped-but-invalid one. Two shapes that were not 400s before are now: a `null` body was a `TypeError` 500 on `PATCH /api/atlases/current`, `PATCH /api/journeys/:id/cover` and `POST /api/uploads/:id/complete`, and - the substantive one - `PATCH /api/journeys/:id/cover` treats an omitted `coverMediaAssetId` as "clear the cover" and used to read that property straight off the parsed body, so a string or array body yielded `undefined` and silently cleared the journey's cover; it is `INVALID_COVER` 400 now. Every previously successful body and every already-validated failure keeps its exact response, including a `{}` cover body, which still clears the cover.
- **Review fixes:** The owner's first review rejected the opening head on two counts, both real. The `core` lane failed on `expected 429 to be 200`: the ten new route cases were introduced with their own sign-up plus a second one for the bootstrap case, and `/sign-up/email` is rate limited to five per ten minutes across the whole suite, so the fifth sign-up in the file - the `media and atlas HTTP endpoints` fixture - was refused. The first correction reused one identity and reached the atlas-less organization by creating a second one, which failed differently (`expected 403 to be 200`): `organizationLimit: 1` means a user owns exactly one. The shipped shape spends ONE sign-up for the whole block, the same count the file had before this PR: `createAuthenticatedAtlas` is split into `createOrganization` plus `bootstrapAtlas`, the block's organization starts without an atlas so the bootstrap case reaches the body guard, and a nested block creates the atlas the other nine cases need. The second count was the missing `docs/pr-history/267.md`, added here as the last commit over the final code head.
- **Follow-up:** `shares.ts` keeps its own `readShareInput`, which is the shape `readJsonObject` follows and which PR #207's ledger describes; collapsing the two into the shared helper is a separate change so that ledger keeps describing live code. The suite no longer asserts `INVALID_JSON` anywhere - the only assertion of it was on `POST /api/journeys` and is repointed to `INVALID_JOURNEY` - because reaching the backstop from a test would mean registering a throwing route on the real `app` singleton. `/api/auth/*` remains its live consumer.

No test suite, dev server, browser, database or Docker was run locally; CI is authoritative. Each route case sends the malformed body, four well-formed non-object bodies (`null`, a string, a number, an array) and one well-shaped-but-invalid body and asserts the identical status and code for all six, then asserts nothing was written: no atlas row for the bootstrapping organization, an unchanged atlas title, an unchanged journey count, an unchanged journey title and revision, an unchanged cover, an unchanged upload count, an unchanged media order, an unchanged media placement, and - for `POST /api/uploads/:id/complete`, whose guard sits before the finalization claim - an upload still `initiated` with a null `completionAttemptId`.
