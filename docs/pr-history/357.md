# PR #357 - Enforce safe account identity linking

Refs #345.

- **Source head:** `d35b31d90ba1588282e0405dc9d4a29a6baf1e76`
- **Scope:** Implements ST-067 as the Backend/Platform identity-safety boundary for one stable Startrips Account with multiple login identities while keeping Better Auth pinned at 1.6.23. `user.id` remains the stable account authority; Better Auth `account` rows remain login credentials/identities. The PR adds redacted `/api/account-identities` listing, password reverification, single-use user/session-bound action grants, explicit provider link intents and verified provider-proof completion, guarded unlink, provider-subject ownership, secret-free audit records, dedicated reverification throttling, and generated database migrations. Native Better Auth identity-management routes are fail-closed for this contract, implicit email linking stays disabled, and provider/email/account UI rollout remains outside this slice.
- **User-visible change:** No new account UI ships in this PR. The server contract now supports safely listing and managing login identities without auto-linking by email, exposing provider/password secrets, allowing cross-account provider-subject collisions, or deleting the last actually usable login. Password reverification for sensitive identity management is rate-limited and action-bound; credential unlink remains unavailable until a provider-based reverification mechanism exists.

## Cross-feature assumption audit

- **Stable account authority:** `user.id` remains the sole Startrips account/tenant identity. Linking or unlinking an authentication method never rewrites Atlas membership, Journey/Home ownership, preferences or primary account identity.
- **Better Auth 1.6.23 boundary:** the pinned generated auth schema is not edited. Custom generated migrations add Startrips-owned durable constraints/audit/action state around it; no dependency upgrade or parallel auth framework is introduced.
- **Provider-subject collision boundary:** `(provider_id, account_id)` is database-unique at the Better Auth account layer and mirrored by explicit ownership semantics, so native OAuth callbacks and ST-067 linking share one durable subject authority. Provider email is metadata only and never decides ownership.
- **Race/replay boundary:** provider linking serializes/reconciles around the durable uniqueness constraint; sensitive grants are hashed, user/session/action-bound and single-use even on validated refusals. Unlink retries succeed idempotently only for the exact consumed action receipt that produced the original unlink.
- **Reverification/oracle boundary:** the custom password reverification route reserves the dedicated stable user/session/address budget before checking a password. External `/api/auth/verify-password` is hidden before the Better Auth wildcard, so a stolen session cannot use the native endpoint as an unbudgeted password oracle and then mint one ST-067 grant.
- **Usable-login guard:** unlink counts only actually usable login methods. Credential unlink remains fail-closed while password reverification is the only shipped management authorization; provider identities must have current verified ownership metadata to count as usable.
- **Provider proof freshness:** a fresh proof for an already-owned provider subject refreshes verification/email metadata without changing subject ownership. Missing/unverified metadata may downgrade usability until fresh verified proof restores it.
- **Privacy/audit:** list output is redacted. Password hashes, provider subjects/emails where not needed, OAuth access/refresh/id tokens and action secrets do not enter the public identity list or secret-free audit trail.
- **Native management boundary:** native Better Auth link/unlink/list/password-verification surfaces do not bypass the Startrips identity-management contract. Server-internal Better Auth APIs remain usable only behind Startrips authorization/rate-limit/action rules.
