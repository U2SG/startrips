# PR #446 - Enroll a first password for a credential-less Startrips Account

- **Source head:** `f294f119822553ba2188195730aa56988c8789ae`
- **Scope:** Adds `server/account-identities/password-enrollment.ts` and a first-password route under `server/routes/account-password.ts`. The service claims the ST-067 single-use reverification grant, checks the server-side recovery precondition and the already-enrolled case, invalidates outstanding Better Auth capabilities keyed to the user id, then lets the pinned 1.6.23 `setPassword` link exactly one `credential` account to the existing user. A durable `password-enroll-intent` audit row is written against the grant before that write and the linked credential row id is recorded on the success receipt, so a consumed grant whose response was lost is reconciled against the authoritative account methods instead of refused. Migrations 0031 and 0032 widen the `account_identity_audit` event check with `password-enroll` and `password-enroll-intent`.
- **User-visible change:** A signed-in user who holds no password credential can set a first password after proving recent control, keeping the same account, Atlas, Journeys and preferences; a user who already has one is kept on the existing change-password path.
- **Review fixes:** A `reset-password` capability could predate enrollment because `request-password-reset` resolves its subject by email alone, so outstanding capabilities are now deleted before the credential write. A consumed grant carrying no success receipt was refused outright, leaving issue #445's unknown-result window unreconciled; it is now reconciled through the intent row plus credential attribution, and never onto a credential another grant enrolled. The lost-race refusal was appending one audit row per retry and is now written under the claim transaction's lock behind an existence guard, keeping one terminal row per consumed grant.
- **Follow-up:** The route is not reachable end to end yet, because the only grant issuer today verifies an existing password; issue #445 leaves that closure to parent #346. One accepted residual window is documented in the service doc comment: a race loser that dies before recording its refusal and retries between the winner's credential commit and the winner's receipt can misattribute a single audit row, which corrupts no state and would need attribution inside Better Auth's own `setPassword` transaction to close.
