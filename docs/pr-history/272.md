# PR #272 - Verify a produced preview's frame against the still that was planned

- **Source head:** `2aa69793b21ad03a36e77cae2f3bdebe26db2ec9`
- **Scope:** Source issue #265. `MultipartStorage.readObject` becomes `readObjectHead({ key, maxBytes })` - a caller-bounded object-head read implemented in `server/storage/s3-compatible-storage.ts` as a ranged `GetObjectCommand` that reports a missing object as the absence case, and clamped to the caller's bound on return; `server/storage/disabled-storage.ts` throws `StorageUnavailableError` from it, now covered by a `server/storage/disabled-storage.test.ts` of its own. `server/media/preview-image.ts` gains `JPEG_HEADER_WINDOW_BYTES` (64 KiB), the window `completeAssetPreview` reads instead of pulling a whole object into memory. `server/media/preview-derivation.ts` gains `plannedStill()`, which recovers the still an asset was planned from its persisted `displayWidth`/`displayHeight` and the configured ceiling, and `previewPixelsWithinPlan()`. `completeAssetPreview` in `server/services/media-preview.ts` now checks the produced frame against that plan after the byte and pixel ceilings and refuses a larger one with the new 409 `PREVIEW_PIXELS_MISMATCH`, cleared through the same `stillHoldsGeneration` compare-and-swap and `discardPreviewObject` drop the existing ceiling failures use. `server/db/app-schema.ts` gains `preview_width` / `preview_height` on `media_assets` (drizzle migration `0014_classy_triton.sql`), written by `beginAssetPreview` with the generation's storage key and cleared with it, so completion compares against the instruction the producer was issued rather than one re-derived from the completing process's live ceiling. The `vi.fn` storage stubs in `uploads-reconciler.test.ts`, `delete-atlas.test.ts`, `delete-journey.test.ts` and `delete-media.test.ts` follow the renamed interface method.
- **User-visible change:** None yet. A produced preview that is larger than the still the server planned is now refused instead of promoted to `ready`, so a reader is never served a frame the plan did not ask for, but no `src/` code produces or consumes a preview yet (#264, #265's sibling ST-049). The original media read contract is untouched in every refusal path.
- **Review fixes:** One P2 thread from `chatgpt-codex-connector[bot]` asked for the issued width and height to be persisted with the pending generation and validated against those immutable values, on the argument that a ceiling change between begin and completion makes the reconstructed plan wrong in both directions. Refuted with no change: `POST .../preview/complete` already builds its ceilings from `previewCeilings()` (`server/routes/uploads.ts:1186`), i.e. the completing process's live config, so `previewPixelsFitCeiling` has been evaluated against that same live value since #263 and this adds no second clock. Writing the plan's longest edge as `min(L, C)`, a lowered ceiling either leaves `previewPixelsFitCeiling` rejecting the frame before the plan check is reached, or forces `min(L, C_old) = L` so the recovered plan is unchanged - there is no configuration in which this rejects a correctly produced frame that `main` accepts. A raised ceiling admits the larger frame for the same reason the pixel ceiling does: it is the policy the deployment now runs. Persisting the pair would also add two columns that can disagree with the arithmetic that produced them, which the queued feature excludes; the equivalence is asserted instead by "recovers the plan from the persisted display size alone". A second thread from the owner's reviewer accepted the lowered-ceiling half of that refutation and held the raised-ceiling half as blocking, and #265 was expanded with the asymmetric invariant: a later config may tighten what is servable but may not widen what an already-issued generation was authorized to create. Fixed as asked. `plannedStill()` is gone; the issued pixel size is persisted with the generation and read back by `issuedStillSize()`, so a ceiling raised from 640 to 1280 between begin and completion no longer admits a 600x467 frame against a 640x320 instruction. The live ceiling stays an independent gate that still refuses an old-plan frame when the ceiling is lowered, under its own `PREVIEW_PIXELS_TOO_LARGE` code. Both directions are pinned by named `core` cases: "holds a raised ceiling to the size the generation was issued" and "still applies a lowered ceiling as the current safety gate".
- **Follow-up:** Equality with the plan's `width`/`height` is deliberately not required - neither edge may exceed it - which is #263's settled boundary for the ceilings applied to the plan, so a producer that rounds a scaled edge differently or returns a source already smaller than the plan is not failed. A still whose JPEG frame header does not appear within `JPEG_HEADER_WINDOW_BYTES` is refused as unreadable rather than read again unbounded; the refusal is retryable through a fresh `POST .../preview`. Only JPEG is understood, which is the one format `PREVIEW_MIME_TYPE` allows and the presigned write binds; a future format would need its own header reader. #264 and the client producer wiring remain, and #260 stays open.
- **Validation:** Locally `./init.sh smoke` only - `pnpm typecheck` on both projects, `git diff --check`, and `node scripts/pr-history.mjs validate-all` / `validate-pr`. Everything behavioural is CI. The `core` lane runs the new `server/storage/disabled-storage.test.ts`, the ranged-GET and caller-bound cases in `server/storage/s3-compatible-storage.test.ts`, the progressive-JPEG and read-window cases in `server/media/preview-image.test.ts`, the `plannedStill` / `previewPixelsWithinPlan` cases in `server/media/preview-derivation.test.ts`, and three named cases in `server/tests/media-preview.integration.test.ts` driving completion through the `MediaPreviewDependencies.storageForBackend` seam: the pinned 600x467 still refused against a 400x300 plan while inside both ceilings with no preview left on either the owner or the guest read path, the same still promoted to `ready` at its measured byte size against a plan that is its own frame, and a row that cannot state its plan refused fail-closed. Twelve `browser-qa` lanes cover the unchanged product surfaces; `ledger` validates this file. No test, browser, database or object store was run locally.
