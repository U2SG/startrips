# PR #226 - Give the guest share prefix its own abuse budgets and harden its lifecycle

- **Source head:** `127101ef3f16d6928885bee13b563942b513e191`
- **Scope:** Phase F of #200. New `server/share-rate-limit.ts` mounted on `sharedRoutes` only: a fixed-window limiter with three request classes — guest data reads and guest media read-URL issuance charged per share grant by the token's SHA-256 hash, and unusable-token requests charged per client address. Four new config knobs (`SHARE_RATE_LIMIT_WINDOW_SECONDS` 10-3600 default 60, `SHARE_DATA_RATE_LIMIT` >=10 default 60, `SHARE_MEDIA_RATE_LIMIT` >=30 default 240, `SHARE_UNKNOWN_TOKEN_RATE_LIMIT` >=5 default 30) validated at startup and wired through `.env.example`, `deploy/env.example`, `deploy/compose.yaml`, `deploy/README.md` and `docs/architecture/portable-auth-storage.md`. New `server/share-rate-limit.test.ts`; a new `share hardening` block in `server/tests/share-grants.integration.test.ts` covering the budgets through the mounted app, the stale-payload cases and three lifecycle races; a new `guest #199` section in `scripts/qa-guest-share.mjs`. New `docs/architecture/share-token-lifecycle.md`; `docs/cross-feature-assumption-audit.md` gains the sharing audit, a twelfth invariant, and corrections to two coverage rows and two "known gaps" that phases D and F have since closed. No schema change, so no migration and no regenerated `server/db/auth-schema.ts`; no product client file touched.
- **User-visible change:** None for an owner or a recipient using a share link normally. A client that floods the guest prefix now receives `429 RATE_LIMITED` with `Retry-After` instead of unlimited service: after 60 payload reads or 240 media read-URLs per minute for one share link, or 30 requests per minute per address whose token names no live grant. A recipient's own traffic never spends the address budget, and one withdrawn photo does not either.
- **Review fixes:** Codex raised three findings, all valid and all fixed in `be5e9ac`. (1) P1 — the address budget was peeked before the handler and charged after it, so every request in a concurrent batch read an un-charged counter, passed, and paid for a database lookup; the budget is now reserved before resolution and released afterwards when the token proves to name a live grant, releasing by one rather than forgetting the key so one valid request cannot wipe a window of probe charges. (2) P2 — sweeping is not a cap when every entry belongs to the current window, so admission now evicts the oldest window once the sweep frees nothing, in O(1) because map insertion order is kept as window-start order. (3) P1 — the delete-and-read case compared two independent database snapshots, which a deletion committing between them fails even though both reads are correct; the pair is now sequential and ordered so the one-way deletion transition makes the implication sound, and the reverse direction is explicitly not asserted. CI found two more: Hono's dispatch converts a handler throw into the response before this middleware sees it, so the `catch` never ran and the probe budget counted nothing — it now settles off `context.error`, with the catch kept for a direct rethrow; and the new guest #199 check reached its Story through the desktop journey rail, which a compact viewport does not render, so it now goes through 全部旅程 and the mobile journey sheet as a recipient on a phone does. A self-review then caught that this navigation was three fixed 400 ms pauses — the same class of defect the owner ruled on in PR 225, where a fixed read racing a React commit reported a lane failure as a product failure — so `127101e` replaces each pause with a wait for the element it is about to click, keeping the diagnostic that enumerates the buttons found on timeout.
- **Follow-up:** The address budget trusts `x-forwarded-for`, which is correct behind the deployment stack's Caddy and would be wrong if the API were ever exposed directly; that would weaken one abuse budget and grants no access. A grant whose remaining lifetime is under one second raises the same `ShareAccessError` as a dead link, so those final sub-second refusals also charge the probe budget — bounded, since the link is dead a second later, but it is a small imprecision rather than a clean separation. The counters are per process; a multi-replica deployment gets one budget per replica, which is the usual in-memory-limiter caveat and would need a shared store to tighten. `soundtrackReadCache` is a module-level cache whose entries survive a scope change until their own `expiresAt`, which is the bounded residual #200 accepts and documents rather than a gap.
- **Validation:** Locally only `./init.sh smoke` — `pnpm typecheck` (client and server projects), `git diff --check`, `node --check` on the touched QA script, and `pr-history validate-all`. No local test run, dev server, browser, database or Docker. CI is authoritative: at `127101e`, run 33959092431, `core` (PostgreSQL 17, migrations, typecheck, full suite, build) and all eight `browser-qa` lanes SUCCESS. The extended `guest-share` lane reports `mobileMode=viewer present=true cluster=true target=44x44 toggled=true manageTriggers=0`, i.e. #199's media-playback affordance renders in the viewer cluster of a shared Story on a portrait phone, keeps its 44px target, toggles `aria-pressed` both ways and has no management surface beside it. The race cases are asserted as invariants that hold for every interleaving — no payload and no signature produced from a state already withdrawn, and no signature reaching past the grant deadline — plus a deterministic post-condition once the batch settles, rather than as an assertion about who wins. Acceptance 5 reads "scope **or revision** changed"; only the scope half is asserted as a denial, deliberately. A guest payload never authorizes anything — membership is re-derived from the asset’s current `journey_id` on every media request — so a scope change is the observable test, while a revision bump is the case where access correctly PERSISTS. Asserting denial on a revision change would encode a wrong invariant, so the tests pin the mechanism that makes both outcomes right instead.
