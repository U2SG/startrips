# PR #238 - Grade tempo-aware playback prefetch in the browser

- **Source head:** `8a00904de0830f0e75460dd07c1927e0c68936bb`
- **Scope:** Issue #197 acceptance item 6, the only one PR #211 left open. New `scripts/qa-playback-prefetch.mjs`, wired as `qa:playback-prefetch` in `package.json` and as a new `playback-prefetch` lane in the `browser-qa` matrix of `.github/workflows/ci.yml`. It drives the dev-only `?qaState=journey-playback&qaMode=prefetch` preview against two new image-heavy Route Point Media fixtures declared in `src/main.tsx` only - 1 route point with 20 images, and 5 route points with 12 images each - and stubs `**/api/uploads/assets/*/read-url` with `page.route` so every signed read resolves after a fixed 2200 ms. Five runs: `fast` and `standard` on the same fixture and delay for the continuity differential, a multi-Route-Point run, a real Quick Recap run at `fast` tempo built through `prepareQuickRecapPlayback` and `quickRecapStepDurationMs` exactly as `LivingAtlasApp` builds it, and a scrub several chapters ahead during `fast` Full Playback. Each run prints one JSON line carrying decode-hold count, total hold ms, per-asset ready lead time, prefetched asset count and the observed window size. `src/journey/JourneyPlaybackOverlay.tsx` publishes `data-playback-hold` on the `.journey-playback` root and moves the hold decision into a new pure exported `playbackHoldReason()`; `hold` is now `holdReason !== "none"`, so the director, the progress fill and the accessible sampler receive exactly the value they received before. Three cases in `src/journey/LivingAtlasApp.test.ts` cover that function in the `core` lane. `readyMsAheadForTempo` and `MAX_PREFETCH_ASSETS` in `src/journey/playbackPrefetchPlan.ts` are untouched, and the lane reads `MAX_PREFETCH_ASSETS` out of that source file so a rename breaks the lane loudly instead of silently disabling its bound. No schema change, no server file touched, no production client path changed.
- **User-visible change:** None. The playback root carries one new `data-playback-hold` attribute, no CSS keys off it, and the two new fixtures exist only under `import.meta.env.DEV` with an explicit `qaMode=prefetch`.
- **Review fixes:** None yet; this is the first submitted head of the PR.
- **Follow-up:** The lane grades the shipped per-tempo budget and tunes nothing: the values in `PLAYBACK_TEMPO_PROFILES` and the lookahead derived from them stay a product-owner decision alongside ST-010 and ST-011, so a run that showed `fast` genuinely worse would be a signal to the owner rather than a licence to move a constant. Measurement is bounded to ten graded beats at each tempo and six or three in the secondary runs, because the `browser-qa` lane has twelve minutes; playing either fixture to its outro is not affordable there. The cold start is deliberately outside the differential, since `fast` reaches its first beat sooner than `standard` and therefore waits longer on the identical first read with nothing wrong. Quick Recap plays a projected Journey, so its beat indexes do not map to the fixture's beat table and its run is graded on hold counts, window bounds and reaching its own beats rather than on per-asset lead time. Video beats are outside this capture entirely: they hold the director for their own runtime, which `playbackHoldReason` now names `video`, and the image-heavy fixtures carry no video.
- **Validation:** Locally only `./init.sh smoke` - `pnpm typecheck` across the client and server projects, `git diff --check`, `node scripts/pr-history.mjs validate-all` and `validate-pr` - plus `node --check` on the new script. No local test run, no dev server, no browser, no database, no Docker; CI is authoritative and runs the full suite, the build, and nine `browser-qa` lanes including this new one. The lane is a detector rather than a tautology by construction: the 2200 ms read delay sits between the `fast` and `standard` image dwells of 1700 and 2800 ms, so a lookahead regressed to the pre-#211 `current + next` slice holds on every `fast` beat and on no `standard` beat, while the shipped time-budget window holds on neither. The run exits non-zero when `fast` exceeds `standard` by more than one hold or 500 ms, when the observed prefetched-asset window exceeds `MAX_PREFETCH_ASSETS` plus the one documented sampling allowance, when any read issued after the scrub belongs to a beat behind the new position, when a decode hold after the scrub is attributed to a beat behind it, when the Quick Recap run reports a mode other than `quick-recap`, or when any run raises a console or page error. That `readyMsAheadForTempo` and `MAX_PREFETCH_ASSETS` are byte-identical in this diff is evidenced by a captured `git diff` of `src/journey/playbackPrefetchPlan.ts` against the merge base.
