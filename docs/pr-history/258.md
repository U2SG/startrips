# PR #258 - Anchor the playback-prefetch seek boundary in the page's event order

- **Source head:** `7b5bcf82213d9faf6e307d2b1d6ea6574d2f5a6e`
- **Scope:** `scripts/qa-playback-prefetch.mjs` only. The init script logs every `read-url` fetch on the page thread together with the `data-playback-step` the overlay published at the moment of the request; the scrub is dispatched from a script that returns the page-thread read count and the trace length taken before the dispatch, so the post-seek boundary is drawn in the page's own event order instead of from a node-side `Date.now()` taken before `page.evaluate`. Staleness itself is unchanged: a post-seek read is stale when its asset's beat is behind the landed step, so the assertion stays a statement about the new narrative position. `staleReads` records `{assetId, assetStep, stepAtRequest}`, with `stepAtRequest` as diagnostics naming the window that issued the read. The landed beat and the post-seek holds are taken from the post-seek slice of the trace. No threshold, tolerance or product code changed.
- **User-visible change:** None.
- **Review fixes:** Kept the page-thread boundary but restored the landed-window staleness predicate. The earlier revision graded a post-seek read as stale only when `assetStep < stepAtRequest`, which would pass a read the pre-seek window issued for a beat ahead of its own step (old step 2 requesting step 6 while the seek lands at step 44) and so weakened the shared `newer intent wins` invariant this lane exists to protect. Replayed onto current `main@d966535d` after #259 merged.
- **Follow-up:** None.
- **Validation:** Locally `node --check`, `git diff --check` and `node scripts/pr-history.mjs validate-all` only; the change is a `.mjs` QA script outside both tsconfig projects and this worktree has no `node_modules`, so no typecheck or browser QA ran locally.
