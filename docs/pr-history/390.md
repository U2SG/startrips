# PR #390 - Expose an owner-scoped cover-reveal display read

- **Base:** `d6ec05a6036c853e905c1ee5b54b8bae1897abaf`
- **Source head:** `61101e6861d4b0960e9308cb505c4891b83af177`
- **Scope:** The Backend read slice of #367 for issue #386 (feature ST-086), and the prerequisite #379 wires its client against. Adds `GET /api/cover-reveal/journeys/:journeyId` to the existing owner router in `server/routes/cover-reveal.ts` behind `requireAtlasAccess(request, "read")`, and `readCoverRevealDisplay()` in `server/services/cover-reveal.ts`. The service re-resolves the Journey in the caller's Atlas, re-runs `evaluateCoverRevealEligibility` over live rows, and serves a derivative only when its lifecycle is `ready` and it is pinned to exactly that asset, that verified stored-byte identity and the current `generationKind`/`generationVersion`; `queued`, `leased`, `failed`, `superseded`, a moved cover, a deleted source, a deleting Journey and a cross-Atlas row all answer `200 { "derivative": null, "reason": … }` so the client falls back to the canonical original, while an unknown, malformed or unowned id answers `404 JOURNEY_UNAVAILABLE` without leaking derivative existence. The display capability is signed through the normal private-storage path (`createPrivateReadUrl`) over the one `output_storage_key` the server chose, never the worker source-read capability, at `MEDIA_READ_URL_EXPIRES_IN_SECONDS`, with `cache-control: private, no-store`. The read writes nothing: no enqueue, no supersession, no lock, no `cover_reveal_writes` row. A new `server/tests/cover-reveal-display.integration.test.ts` and the extended `docs/architecture/cover-reveal-worker-protocol.md` complete the change. The suite covers the exact ready revision, no derivative (with a proof of zero enqueue side effect), `queued` / `leased` / `failed`, a superseded row that stays undisplayable even once the cover returns, a cover replaced after a metadata read, source and Journey deletion, cross-Atlas access, a worker credential and a real share token both refused on the browser route, the one-object display capability and its TTL, the closed metadata field set, and — added in `61101e6`, spied the way `server/request-log.test.ts` spies — that the read writes no key, URL, hash or token to the console, which is the other half of #386's no-secrets requirement. No existing route, service function or worker path is modified; no existing route, service function or worker path is modified.
- **User-visible change:** None yet. The renderer and the Journey cover / Story opening that consume this belong to #367/ST-073 and #379/ST-083; this PR only supplies truthful metadata and a display capability.
- **Authority separation:** Browser display authority is disjoint from worker processing authority in both directions, and the protocol document now states it as a table under *Principals*. The browser presents a Better Auth session and names a Journey of its own Atlas; the worker presents `COVER_REVEAL_WORKER_TOKEN` and names a job plus the lease token it holds. The worker credential and a guest share token are both bearer tokens and this server has no bearer-to-session path (`server/auth.ts` loads the `organization` plugin only), so either presented on the browser route resolves no session and answers byte for byte as presenting nothing does. Neither principal names a storage key. The display metadata is a closed field set — id, journeyId, generationKind, generationVersion, presetId, sourceMediaAssetId, sourceContentHash, mimeType, width, height — carrying no `seed`, `attempts`, `lastErrorCode`, storage key, lease hash, signed source URL or upload target, and no new log statement takes a URL or a key.
- **Cross-feature assumption audit:** The changed dimension is semantic reveal and data coverage — a Journey cover now has a second possible image source whose validity is pinned to one exact cover revision, invalidating the assumption that a signed read of a Journey's cover is valid as long as the Journey is. Siblings actually checked: `signPrivateMediaRead` / `GET /api/uploads/assets/:id/read-url` (untouched; the new read signs a `cover-reveals/` key from a derivative row, never a `media_assets` key, and passes the same owner TTL); the `previews/` reconciler (unaffected — this read creates no write record and no object); `reconcileCoverRevealDerivatives` and `completeCoverRevealJob` (deliberately not raced — the read declines a stale `ready` row rather than superseding it, so it never competes for the Journey and media row locks the completion transaction takes); `server/routes/shares.ts` and the guest surface (no grant widening, no new share route); and the worker router (unchanged). The residual is the ordinary signed-URL window every private read in the product has: a cover replaced a moment after a signature is minted leaves that one URL alive for its TTL, bounded by the owner media-read policy, and the next read returns none. No regression-family search applies — #386 is a new Backend contract, not a P0/P1 regression against code on `main`.
