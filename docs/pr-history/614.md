# PR #614 - Widen the canonical Story sequence to presentation entries

- **Source head:** `b67c1aaa47214547ddf32e27995a02d90a3c362f`
- **Scope:** Foundation PR for #595 and #555, now based directly on `main`. `src/journey/journeyPlayback.ts` gains `StorySequenceEntry`, `storySequenceForJourney`, `storySequenceMedia`, `storyEntryDensity`, and the private `playbackChapterByOwner` / `playbackChapterMembers` that `playbackMediaByChapter` now shares. Story's cursor is an index into a flat `JourneyMediaAsset[]` (`scopedMedia` / `activeAsset` in `JourneyStory.tsx`), a shape that cannot express a Route Point holding a note but no media, nor a presentation whose identity is not the asset's identity. The sequence is widened here so both issues grow on one sequence instead of each building beside it. The owner's recommended fix shape for the open #76 regression explicitly names `playbackStoryMedia` as the canonical ordering this cursor should be derived from, so this widens the function that fix will need rather than working around it. It was originally stacked on #612 because `pr-history.mjs` rejects a PR that modifies another PR's ledger; now that #612 has merged as `1c709ef2` and its ledger is part of `main`, this targets `main` directly and the diff is unchanged.
- **User-visible change:** None. No rendering is wired to the sequence yet; #595 consumes the note entries and #555 adds the Journey-cover presentation entry on top of this. `playbackStoryMedia()` is now the media-only projection of the sequence, and a test asserts that projection is identical to both the previous list and the order `buildPlaybackSteps` hands the director, so this is a widening rather than a silent reordering.
- **Review fixes:** Keepsake enforces a linear owner-read budget (`journeyKeepsake.test.ts:310`, at most 4x the media count) and the first two drafts violated it - 1310 reads, then 984, against a 664 ceiling. The first cause was scanning a chapter's media once per chapter member; the second was reading `asset.routePointId` inside `storyMediaEntry` when the owner is already the bucket key being iterated. Reading the owner from the bucket returned it under budget with no assertion weakened, and is why the sequence does not call `playbackMediaByChapter`: per-owner buckets are already `sortOrder`-sorted, and walking chapter members in canonical route order concatenates them into exactly the `(route position, sortOrder)` order that function produces. Two further draft errors were in the tests rather than the code: an assertion that compared the whole sequence against `buildPlaybackSteps` including intro media, which rides on its own `intro` step and not on a `stop` step, and a fixture whose second Route Point had a note but no media and therefore correctly emitted a note entry. An earlier final also sealed the ledger in two consecutive ledger-only commits, and was then pushed together with its code, so `verify` could not find a reusable Source CI run for it; the branch was rolled back and re-pushed as a code-only Source head followed by a single ledger-only final.
- **Follow-up:** **#76 is open and remains a P1 regression; #595 and #555 are not started.** The owner's clarification of 2026-09-28 on #76 supersedes the earlier Story scope/terminal wording: in normal Story viewing a selected Route Point is a chapter/jump position, not a hard media boundary, and `selectedRoutePointId` truncating `scopedMedia` so every Route Point becomes an island that loops on itself is the defect to fix, with point-only scoping surviving only in an explicit management/filter mode. Whole-Journey autoplay is likewise to loop at the Journey boundary rather than hold on the last frame. **#595 must not preserve `selectedRoutePointId === null` as the whole-versus-point switch** - that switch is the bug, not the guard, and the `no implicit wrap` tests in `storyMediaPolicy.test.ts` encode the superseded wording and will need to change with it. #595 needs Story's `scopedMedia`, `assetIndex`, `indexStoryMedia`, the autoplay advance and the warm window to be entry-indexed. #555 additionally needs a `journey-cover` role, the fresh-open versus return-intent distinction that `LivingAtlasApp.tsx:2781-2784` currently collapses, and role-keyed cover reveal.
